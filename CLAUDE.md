## Compact Instructions

При сжатии обязательно сохрани:

**Архитектурные решения**
- Групповые чаты: таблицы `chat_groups` + `chat_group_members` (роль `owner`/`member`, минимум прав). `chat_id` вида `group_<id>`. Переиспользуют существующий пайплайн сообщений/сокетов (`chatParticipants.js` научили распознавать `group_\d+`) — отдельной системы рассылки нет.
- Чтение в общих/групповых чатах: `messages.status` — общая колонка на всё сообщение, не годится для «прочитано мной» при нескольких получателях. Добавлена таблица `message_reads` (per-user) + `services/readReceipts.js` с `isSharedChat()`/`markRead()`. Личные чаты (1:1) по-прежнему считаются по `status`.
- Мобильный фокус/жизненный цикл: на Android нельзя полагаться на DOM `focus`/`blur`/`visibilitychange` — используется `CapApp.appStateChange` как источник истины. Приложение шлёт его на сервер сокет-событием `app_state`; сервер решает, слать ли пуш, по `canReceiveInApp` (живой сокет ещё не значит, что JS не заморожен в фоне), а не просто по `isUserOnline`.
- Навигация мобильного экрана: `hideMobileKeyboard()`/`goToSection` — более ранние легитимные фиксы, но настоящая причина «чат-ловушки» была глубже: переписка на узком экране была в DOM всегда и пряталась CSS-трансформом (`translateX`), и при потере трансформа композитором WebView оставалась поверх списка, хотя state уже был «список». Исправлено переходом на условный рендер — на узком экране (`useNarrowLayout` в `Chat.tsx`, синхронизировано с `@media (max-width: 760px)` в theme.css) существует только одна панель зараз, прятать нечего.
- Непрочитанное в общих/групповых чатах — читать нужно `read_by_me` (personal per-user отметка из `message_reads`, отдаётся в истории), а не `messages.status`: тот значит «прочитано хоть кем-то», и отбор по нему навсегда «застревал» на сообщениях, прочитанных другим участником. Тот же принцип и в `server/services/readReceipts.js`.
- **Состояние окна Electron восстанавливается при запуске** (`window-state.json`, поле `mode`: `normal`/`minimized`/`tray`): после перезагрузки машины или установки обновления приложение возвращается туда, где его оставили. Режим пишется на КАЖДОЕ изменение (`minimize`/`restore`/`hide`/`show`), а не при выходе: перезагрузка и `quitAndInstall` завершают процесс помимо нашей воли, и «сохраню при закрытии» не сработало бы. `mode: 'tray'` означает не показывать окно вовсе — показать и тут же спрятать значит моргнуть окном на весь экран при каждом старте с автозагрузки. Геометрия у свёрнутого/спрятанного окна НЕ перезаписывается: Windows уводит свёрнутое окно за экран, и `getBounds()` вернул бы мусорные координаты, с которыми окно потом открылось бы вне видимой области.
- Уведомления Electron нельзя показывать из рендерера: `loadFile()` даёт origin `file://`, Chromium считает его небезопасным и намертво блокирует `Notification` API (`permission` вечно `denied`). Показ уведомлений перенесён в главный процесс (`main.js`, IPC `notify:show`/`notify:close`/`notify:close-all`, `preload.js`).
- Задачи (`server/routes/tasks.js`) — поручения, отдельная сущность от календарных «задач» (`is_task` на событии). Видимость строго по составу `task_participants`: создатель + причастные, никто больше. Статус меняет любой причастный, не только автор.
- Аккаунты `account_type = 'internet'` видят урезанный NavRail (`INTERNET_VISIBLE_SECTIONS` в `NavRail.tsx`) и не получают общий календарь — фильтрация на сервере (`canSeeGlobalCalendar` в `routes/calendar.js`), а не только в интерфейсе.
- **Справочник (`GET /api/users`) разделён по типу аккаунта в ОБЕ стороны и БЕЗ ИСКЛЮЧЕНИЙ** (с 15.08.2026): «Интернет» видит только «Интернет», «Сотрудник» — только сотрудников. Прежнее исключение для администрации (орг-роль `admin`/`moderator` либо группа «Админы», `ADMINISTRATION_SQL`) снято целиком по требованию пользователя — см. раздел про меню строки списка чатов. `/api/contacts` под это правило по-прежнему НЕ подведён: уже добавленные контакты остаются видны обеим сторонам.
- Картинки в чате: `messages.file_path` существовал в схеме с самого начала, но был не подключён — теперь используется (+ `file_width`/`file_height`). Путь от клиента для `chat_message` не доверенный: `isValidChatImagePath` (`routes/messages.js`) сверяет формат и то, что файл реально существует на диске. Удаление сообщения саму картинку с диска больше не трогает — см. пункт про удаление сообщений ниже.
- Редактирование сообщения — панель над полем ввода (как в Telegram), а не строка в самом пузыре: правка живёт в `Chat.tsx` (`editingMessage` state), `ChatWindow` только сообщает id+текст наверх через `onStartEdit`.
- **Кастомные смайлики картинками**: элемент пака бывает двух видов, различаются по `emoji_items.file_path` — юникодный (`emoji` заполнен) или картиночный (`name` + `file_path`). Разделение НА УРОВНЕ ЭЛЕМЕНТА, а не пака: вид виден по нему самому, запрещать смешивание нечем. В `messages.text` уезжает КОД `:name:`, а не картинка — формат хранения переписки не меняется (там трёхлетний архив, трогать запрещено). Имя уникально глобально (частичный уникальный индекс по `name`): в тексте пака нет, искать картинку надо по одному имени. Регэксп кода намеренно узкий (`[a-z0-9_]{2,32}`) — иначе цеплял бы `:D` и порты в ссылках `host:8080`; и на сервере, и на клиенте (`utils/customEmoji.ts`) он обязан совпадать. Неизвестный код остаётся текстом: подменять его пустотой — значит менять содержимое чужого сообщения. В норме неизвестных не бывает — см. пункт про каталог отрисовки ниже. Отрисовка через массив React-узлов, НЕ через строку HTML (это была бы инъекция). `replaceItems` (правка юникодной строки в панели) чистит только `file_path IS NULL`, иначе сохранение строки сносило бы загруженные картинки. `emoji` объявлена NOT NULL — у картиночного элемента там пустая строка.
- **Каталог отрисовки ≠ каталог выбора** — два РАЗНЫХ вопроса, и отвечать на них одной выдачей нельзя. `GET /api/emoji` (только `enabled` паки, без `retired`) — «что можно вставить сейчас», для панели выбора. `GET /api/emoji/catalog` — «как показать то, что уже отправлено»: ВСЕ картиночные элементы, какие когда-либо существовали, независимо от `enabled` пака и `retired` элемента. Раньше отрисовка строилась из первой выдачи, и выключение пака переводило всю старую переписку обратно в текст `:name:`. Разделение выдач остаётся в силе и сейчас: даже когда пак выключен, отправленные сообщения обязаны показывать картинки. **Но правило «строка и файл не удаляются никогда» отменено 12.08.2026** — см. пункт про настоящее удаление ниже: `DELETE /custom/:itemId` теперь физически сносит строку и оба файла, и старые сообщения с этим кодом станут текстом (осознанное решение пользователя). Удаление пака целиком по-прежнему переносит его картиночные элементы в служебный пак «Архив смайликов» (`enabled = 0`, заводится по требованию) — иначе `ON DELETE CASCADE` унёс бы их вместе с паком незаметно для админа; сам архивный пак удалить нельзя.
- **Удаление смайлика с 12.08.2026 — НАСТОЯЩЕЕ: строка из БД и оба файла с диска, имя освобождается.** Решение пользователя, принятое с полным знанием цены: в уже отправленных сообщениях на месте картинки останется текст `:name:` (сам текст сообщения не меняется — там и лежит этот код), а освободившееся имя может достаться другой картинке, и тогда старые сообщения покажут её. Прежнее правило «имя занято навсегда» отменено как избыточное. Смягчение ровно одно: перед удалением панель спрашивает `GET /api/emoji/admin/custom/:itemId/usage` и показывает в подтверждении, в скольких сообщениях код встречается, — решение необратимое, и цена должна быть на экране до нажатия, а не после. Для юникодных элементов вопрос не стоит вовсе: в сообщение уезжает сам символ, а не ссылка на строку, и удаление такого элемента старую переписку не трогает. Колонка `retired` осталась ради уже спрятанных строк (их видно в панели, откуда можно вернуть или снести), новые туда не попадают.
- **Анимация — ОТДЕЛЬНЫЙ файл поверх статичного (`emoji_items.animated_path`), а не замена.** Нужны обе версии сразу: в панели выбора всегда показывается статичная — десяток дёргающихся картинок разом не даёт ничего выбрать, — а анимированная живёт только в переписке. Поэтому статичную версию при загрузке ОБЯЗАТЕЛЬНО прогонять через sharp БЕЗ `{ animated: true }` (берётся первый кадр), иначе загруженная гифка задёргается и в выборе; анимированную — с ним (проверено: 2 кадра на входе → 2 на выходе, chunk `ANMF` в webp). Показ анимации — личная настройка устройства (`UiPrefs.animatedEmoji`, по умолчанию включена), и она НЕ проп: смайлики рисуются в десятке мест (лента, ветка, цитаты, превью, реакции), поэтому флаг модульный (`setEmojiAnimationEnabled` в `utils/customEmoji.ts`) — прокидывать его в каждое место значит забыть в половине. Выключено — показывается статичная, она есть всегда.
- **Экран «Смайлики» в панели — аккордеон из паков (открыт один) + плитки и карточка смайлика в модалке.** Паков мало, но в каждом сотни картинок: развёрнутые разом они не помещаются никуда, а плитка с полями внутри превращала экран в кашу. Плитка минимальна (картинка + имя), всё остальное — в модалке по нажатию: имя (только чтение — оно в текстах сообщений), базовый смайл, статичная и анимированная версии, удаление. Базовый смайл выводится из имени вида `u_1f4a2` → 💢 (`fallbackFromName`, одинаково на сервере и клиенте) — имена файлам дают по коду эмодзи, и вбивать его руками не нужно. Поле ввода юникодной строки убрано: теперь юникодный смайлик — такой же элемент пака, просто без картинки (в сообщение уезжает сам символ). Порядок — перетаскиванием, кнопки «раньше/позже» убраны: в паке под сотню картинок, доводить нужную кликами — работа на весь день. Порядок ОБЩИЙ для обоих видов.
- **Перетаскивание в панели работает и пальцем — но только после удержания (~260 мс).** Мышью тянем сразу, пальцем — нет: иначе первое движение по сетке хватало бы смайлик вместо прокрутки, и до нижних рядов было бы не добраться. Прокрутка глушится своим НЕ-пассивным `touchmove` на контейнере и только на время перетаскивания — React вешает `touchmove` пассивно, и `preventDefault` из его обработчика не работает вовсе (та же история, что с выделением сообщений в переписке). Прежняя заметка «DnD на телефоне надёжно не ловится, поэтому кнопки» отменена — ловится, если жест разводить по типу указателя.
- **Уборка смайлика обратима — иначе это дорога в один конец.** Имя закреплено за смайликом навсегда (см. выше), поэтому привычное «убрать и загрузить заново под тем же именем» упиралось в 409 и не оставляло НИ ОДНОГО способа вернуть картинку в оборот: убранный элемент не показывался и в панели админа. Добавлено: `retired_custom` в админской выдаче (`adminPacks()` — отдельная функция, а не флаг по месту: включать убранные обязаны ВСЕ админские ручки и НИ ОДНА пользовательская), ручка `PUT /api/emoji/admin/custom/:itemId/restore` и раздел «Убранные» в паке. Правило при этом НЕ ослаблено: возвращается ТА ЖЕ строка (тот же id, то же имя), а не имя, выданное другой картинке, — старые сообщения не меняются. Для лежащих в архиве (пак удалили целиком) пак назначения обязателен: архив выключен, и возврат «на место» оставил бы смайлик так же невидимым. Отказ загрузки теперь машиночитаемый (`code: 'name_retired'` + `itemId`), и панель предлагает вернуть смайлик, поставив ему уже выбранный файл, — потому что «убрал, чтобы загрузить новую картинку» и есть настоящее намерение в 99% случаев (а менять картинку под тем же кодом умеет `POST /custom/:itemId/image`, убирать для этого ничего не нужно).
- Базовый юникодный эмодзи картиночного смайлика (`emoji_items.fallback_emoji`, как у `custom_emoji` в Telegram) — для мест, где картинку показать нечем: уведомления ОС, буфер обмена (`toPlainText` в `utils/customEmoji.ts`), `alt`, описание задачи из сообщения, пропавший с диска файл (`onError` подменяет `<img>` на `<span>`). Не задан — подставляется `DEFAULT_EMOJI_FALLBACK` на клиенте, бэкфилл старых строк не нужен. Правится отдельной ручкой `PUT /api/emoji/admin/custom/:itemId`, в отличие от ИМЕНИ, которое неизменяемо навсегда.
- Замена картинки под тем же `:name:` (`POST /api/emoji/admin/custom/:itemId/image`) — НЕ заводит новую строку, только переписывает `file_path` у существующей: код в старых сообщениях один и тот же, меняется лишь то, что за ним показывается. Старый файл при этом удаляется с диска (в отличие от уборки смайлика) — на него больше ничего не ссылается, код резолвится в актуальный `file_path` на лету. Порядок картиночных элементов внутри пака — кнопками «раньше/позже» (`PUT /api/emoji/admin/:packId/custom/reorder`, принимает список id целиком, как и `replaceItems` для юникодной строки), — заменено перетаскиванием 12.08.2026, см. пункт про жест выше. Позиции переиспользуют то же поле, что у юникодных элементов пака, — не конфликтует, потому что сравнение позиций идёт только внутри одного вида элемента (bucketing по `file_path`/`emoji` в `packsWithItems`).
- Правка смайликов в панели рассылается всем сокет-событием `emoji_changed` (широковещательно — каталог общий, персонализации нет). Клиент по нему перечитывает `/emoji/catalog` И сбрасывает отдельный модульный кэш панели выбора (`invalidateEmojiPackCache` в `EmojiPicker.tsx`) — это два независимых кэша, и забыть второй значит показать старый состав.
- Код `:name:` — внутренний формат хранения, человек не должен видеть его НИГДЕ, включая поле ввода (см. следующий пункт). Отсюда: цитаты в панелях правки и ответа над полем ввода, превью в «Переслать», превью последнего сообщения, плашка реакции — всё через `renderTextWithEmoji`. Обрезка текста по длине обязана убирать незакрытый хвост кода (`/:[a-z0-9_]{1,32}$/`) и на клиенте, и на сервере (`index.js`, `MAX_MESSAGE_LENGTH`) — огрызок `:cat` уже не станет картинкой и остался бы в БД навсегда. Квантификатор именно `{1,32}`, а НЕ `{0,32}`: с нулём регэксп совпадал с одиноким закрывающим двоеточием в конце строки и срезал его у только что вставленного целого кода — смайлик молча оставался текстом и не отправлялся.
- **Поле ввода — contentEditable, а не `<textarea>`** (`EmojiComposerField.tsx`), потому что в textarea картинку посреди текста показать нечем в принципе. Наружу поле отдаёт всё тот же текст с кодами (`domToText`), поэтому сервер, сокеты и БД о нём не знают — формат хранения переписки не меняется. Содержимое НЕ рисуется React'ом (нет ни `value`, ни `dangerouslySetInnerHTML`): перерисовка на каждое нажатие сбрасывала бы курсор, поэтому React владеет только пустым контейнером, а наполнение императивное через ref-хендл (`hydrate`/`clear`/`insertPicked`). Смайлик — лист с `contenteditable="false"` и `data-emoji-name` (имя берётся оттуда, а НЕ из пути к файлу: путь меняется при замене картинки под тем же кодом). Backspace/Delete дополнительно перехвачены руками, хотя браузеры умеют удалять такой узел целиком и сами, — обещание «одно нажатие» не должно зависеть от версии движка. Enter/Shift+Enter всегда `preventDefault`, перенос строки вставляется литеральным `\n` (контейнер с `white-space: pre-wrap`): дай браузеру волю — он наплодит `<div>/<br>`, и обратная сборка текста усложнится на ровном месте. Вставка из буфера всегда через `text/plain`, иначе contentEditable потащит внутрь чужую разметку. **На мобильном (`isNativeMobile`) по-прежнему `<textarea>`** — contentEditable в Android WebView капризнее (курсор, автозамена, системная клавиатура), а чинить это вслепую нельзя; распространение на телефон — отдельная задача.
- Смайлики — паки в таблицах `emoji_packs`/`emoji_items`, юникодные хранятся текстом. Обычный пользователь видит только `enabled` паки (`GET /api/emoji`), правка паков — только супер-админ (`/api/emoji/admin/*`, вкладка «Смайлики» в панели). Задачи по смене статуса задачи и созданию/правке шлют `tasks_changed` всем причастным — раньше клиент это событие никто не слушал, статус не обновлялся без смены вкладки.
- Смена статуса задачи в диалоге (`TaskDialog.tsx`) — явный picker со всеми тремя статусами (`TASK_STATUS_ORDER`/`TASK_STATUS_LABELS` в `tasks/types.ts`), можно поставить любой напрямую, включая назад. Сервер (`PUT /api/tasks/:id/status`) и так принимал любой статус без ограничения направления — ограничения не было нигде, кроме UI: список умел только листать по кругу вперёд кнопкой-пилюлей, и не было заметно, что смена вообще возможна.
- Архив задач: `tasks.archived`, `PUT /api/tasks/:id/archive` — переносить может любой причастный, но только когда `status = 'done'` (проверка на сервере). Возврат статуса с "готово" на любой другой автоматически снимает архив — иначе задача молча зависала бы видимой только во вкладке "Архив", хотя снова не done. Список `GET /api/tasks` по умолчанию отдаёт неархивные, `?archived=1` — архивные.
- **«Кто может писать» — единый механизм прав** (`server/services/chatPermissions.js`, `chat_groups.write_policy`): `all` / `members` (список в `chat_group_writers`) / `departments` (`chat_group_writer_departments`) / `admins` (орг-роль `users.role`) / `nobody`. Неявных исключений НЕТ НИ У КОГО, включая владельца группы и администрацию: «только администратор» — отдельный вариант политики, значит в остальных режимах право молча не выдаётся, а владелец добавляет себя в список сам. Испорченное значение в колонке трактуется как `nobody`, а не как «всем можно» — мусор в базе не должен открывать доступ. Списки переписываются целиком и только для своей политики (смена режима их очищает), в список пишущих нельзя занести того, кто не состоит в группе. Право писать НЕ включает проверку участия в чате — её отдельно делает `isParticipant` в `index.js`. Клиент свою копию правил не держит: `can_post` считает сервер под конкретного зрителя и отдаёт в REST-выдаче `/groups`; в сокет-событии `group_updated` его нет (оно одно на всех), поэтому клиент после него перечитывает список групп.
- Канал-объявление в группах: `chat_groups.announcements_only` — с появлением `write_policy` флаг ОТВЕЧАЕТ ТОЛЬКО за счётчик просмотров (глаз с числом), право писать с него снято. Миграция проставила существующим каналам `write_policy = 'admins'`, поэтому на проде поведение не изменилось. В интерфейсе флаг подписан «Показывать счётчик просмотров», чтобы не читался как право.
- Проверка права писать обязательна НА СЕРВЕРЕ (обработчик `chat_message` в `index.js`) — дизейбл композера на клиенте (`Chat.tsx`, `activeChatMeta.canPostHere`) только для UX, обойти его тривиально. При отказе сервер шлёт `message_blocked` с `reason: 'write_not_allowed'`. `canPostAnnouncement` в `routes/groups.js` осталась, но теперь относится только к ПРАВАМ УДАЛЕНИЯ чужих сообщений — к отправке она отношения не имеет, не перепутать.
- Удаление сообщений — юридическое обязательство ПОЛЬЗОВАТЕЛЯ: закон требует быть готовыми предоставить переписку целиком по требованию (не только метаданные о факте передачи — время/отправитель/получатель/IP, но и само содержимое), поэтому "удаление" сообщением НИКОГДА не трогает ни `text`/`file_path`, ни файл на диске, ни саму строку — `message_delete` (index.js) и групповой bulk-delete (`routes/groups.js`) ставят только флаг `deleted=1`. Содержимое остаётся в БД физически навсегда, но не должно попасть НИКУДА наружу приложения: `routes/messages.js` редактирует ответ на лету для всех трёх выдач (история курсором/offset, `/meta/last`) — если `deleted`, в JSON уходят пустые `text`/`file_path`, реальные значения из БД читаются только этим редактированием и никогда не сериализуются как есть. На клиенте такие сообщения дополнительно не рендерятся вовсе — ни плейсхолдером "Сообщение удалено", ни как-то иначе (`ChatWindow.tsx` фильтрует `deleted` из `messages` до рендера) — это уже вторая, декоративная линия защиты поверх редактирования на сервере. `messages.sender_ip` — отдельная колонка для метаданных о факте передачи, пишется при отправке (`clientIpOf(socket)` в `index.js`, читает `x-forwarded-for` от nginx, т.к. `socket.handshake.address` за прокси — это адрес самого nginx, не клиента); тоже никогда не отдаётся наружу. Массовый выбор своих сообщений для удаления доступен всем в любом чате (не только владельцу группы); чужие может выбрать только владелец группы — тогда используется REST-ручка (`/groups/:id/messages/delete`), иначе клиент просто шлёт `message_delete` по каждому id. Полное удаление аккаунта/группы (панель супер-админа, `services/accountArchive.js`, `routes/groups.js` DELETE /:id) под это правило не подведено — там по-прежнему настоящий `DELETE FROM messages`, это осознанно оставлено вне рамок этой задачи (см. «Незакрытые вопросы»).

**Уведомления и застрявшая отправка**
- **Дубли пушей лечатся ОТСРОЧКОЙ, а не отказом от одного из каналов** (`schedulePush` в `server/index.js`). Android сообщает о сворачивании сразу (`app_state`), но JS в свёрнутом WebView замирает НЕ сразу: секунды, а иногда минуты приложение продолжает получать сокет-события и рисовать локальные уведомления само. Сервер в этот момент уже считал клиента неспособным показать уведомление и слал пуш — в шторке оказывались обе карточки, и схлопнуть их нечем: локальная адресуется по id сообщения, пуш — по `tag` чата. Ждать, пока сокет отвалится по `pingTimeout`, тоже нельзя — тогда уведомление теряют те, кого система заморозила молча. Поэтому свёрнутому, но ещё ЖИВОМУ клиенту (`isUserOnline`) пуш откладывается на `PUSH_GRACE_MS = 3000`; успел показать сам — шлёт `message_notified`, и отложенный пуш снимается. Тем, у кого сокета нет вовсе, пуш уходит сразу: подтверждать там некому. Таймер `unref()`, иначе он держал бы процесс при остановке сервера.
- Пропажа уведомлений при включённом VPN — НЕ наш код: FCM держит своё постоянное соединение с серверами Google, и VPN с полным туннелем рвёт именно его, не сообщая об этом ни нам, ни приложению. Чинить нечем; отсрочка выше как раз и оставляет в этом случае рабочим локальный канал.
- Глушение уведомлений работает и в общем чате (`shouldNotifyUser(id, 'general', …)`) — закреплено тестом в `tests/notificationPolicy.test.js`, раньше сквозной путь «карточка чата → REST → проверка перед пушем» ничем проверен не был.
- **Неотправленное сообщение можно ОТМЕНИТЬ** (`onCancelOutgoing` → `removeOutgoing`). Очередь отправки с состояниями `pending`/`failed` существовала и раньше, но у сообщения с вложением любая неудача сразу помечается `failed` навсегда, а меню на таких сообщениях не открывалось вовсе — застрявшую картинку нельзя было ни убрать, ни скопировать её текст. Теперь у них СВОЙ короткий список меню (`buildMenuItems` выходит раньше всего остального): «Отправляется…»/«Не отправлено», «Копировать», «Повторить отправку», «Отменить отправку». Ни ответить, ни переслать, ни удалить нельзя — на сервере сообщения ещё нет, а id у него временный; по той же причине не показывается и ряд реакций. Долгое удержание на таком сообщении не заводит выделение (флаг `noSelection` в `handleTouchStart`), но тап по-прежнему открывает меню.
- **Загрузка картинки терпит НЕДОПИСАННЫЙ файл** (`sharp(buffer, { failOn: 'none' })` в `routes/messages.js`). На части устройств (ловили на Vivo V21e) «сделал скриншот и сразу поделился» отдаёт файл раньше, чем система дописала его на диск, — то же изображение, пересохранённое в редакторе, уходило сразу, им и опознали причину. Проверено на обрезанных до 60% файлах: `sharp` по умолчанию давал `VipsJpeg: premature end of JPEG image` и `vipspng: libpng read error`, с `failOn: 'none'` оба разбираются и отправляются (1080×2340 → 738×1600). Обрезанный WebP не спасается и так — libwebp отказывается декодировать битый VP8 целиком, но скриншоты телефона это JPEG/PNG. `stats()` (нужен только ради признака прозрачности) обёрнут отдельным try — он читает КАЖДЫЙ пиксель и спотыкается чаще самой перекодировки; не смогли выяснить — считаем кадр непрозрачным и всё равно отправляем. Неразбираемый файл теперь отдаёт 400 с человеческим текстом, а не 500 с сырой ошибкой sharp.
- **Пустое зарезервированное место под клавиатуру обязано быть НЕВИДИМЫМ.** `.mobile-emoji-surface` красилась в `--sidebar` всегда, хотя в режиме клавиатуры она лишь держит место, которое IME накрывает собой. Высота места берётся от ПРОШЛОЙ клавиатуры (`onKeyboardWillShow`), и стоит новой оказаться ниже — над ней оставалась полоса цвета панели, читавшаяся как пустая панель непонятного назначения (её и видели на 1.8.1). Теперь фон только у `.is-emoji-visible`: любое расхождение высот показывает переписку, а не панель.

**Обои переписки**
- `users.chat_background_path` — свои обои под лентой, ОДНИ на все чаты человека. Хранятся на сервере, а не в localStorage (в отличие от прочих настроек вида): картинку ставят один раз и ждут её на всех своих устройствах. Исходник не хранится никогда — sharp ужимает до 1080×1920 (`fit: inside`) в webp качества 62: это фон за текстом, разницы не видно, а при сотне сотрудников исходники с телефонов — это гигабайты (проверено: 1200×2000 JPEG 35.8 КБ → 1080×1800 webp 7.7 КБ).
- **Применяются переменными CSS на корне документа (`utils/chatWallpaper.ts`), а не пропсом.** Лента рисуется не в одном месте (переписка, ветка, узкий экран), и прокидывать фон в каждое значило бы забыть в половине — та же причина, что у модульного флага анимации смайликов. Каждое свойство `.conv-body` берётся из переменной СО СВОИМ запасным значением (`var(--chat-wallpaper-size, 340px 340px, …)`), поэтому снятие обоев — это просто удаление переменных, а узор по умолчанию возвращается сам. Не забыть, что запасных значений четыре, а не одно: без `background-attachment` снимок уезжал бы при прокрутке (`local` у узора против `scroll` у фото), без `background-repeat` — размножался бы плиткой.
- Замена пишет НОВЫЙ файл (в имени время) и удаляет прежний: на обои, в отличие от картинок в переписке, не ссылается ни одно сообщение. Путь запоминается и в localStorage — иначе при каждом открытии фон моргал бы узором, пока едет ответ `/users/me`.

**Синхронизация с Google Календарём**
- Подключается ОДИН гугл-аккаунт на организацию, из панели супер-админа (вкладка «Google Календарь»); его ОСНОВНОЙ календарь синхронизируется с общим (`scope_kind = 'global'`) двусторонне, дополнительные — только читаются, каждый своим слоем (см. следующий пункт). Личные события сотрудников наружу не уезжают: у гуглового аккаунта организации нет понятия «личное событие сотрудника», и подставлять туда чужие встречи значило бы раздать их всем, у кого есть доступ к тому календарю. Колонка `user_id` в `google_calendar_accounts` заложена под персональные подключения заранее (значение `0` = аккаунт организации, именно `0`, а НЕ `NULL`: в UNIQUE-индексе SQLite значения `NULL` считаются различными, и второй такой же аккаунт спокойно завёлся бы рядом).
- **Календарей несколько, а не один: таблица `google_calendar_sources`.** Ровно как в самом Google, где рядом с календарём аккаунта живут «Другие календари» — чужие, подписанные, доступные только на чтение. Основной (`is_main = 1`) отличается двумя вещами: в него уходят НАШИ события и его содержимое ложится в общий календарь; дополнительные получают каждый свой слой `gcal:<id>` со своим цветом. Основной — тоже строка этой таблицы, а не отдельная ветка кода: пайплайн чтения один, и держать для него второй путь значило бы чинить каждую ошибку дважды. Курсор `sync_token` у каждого календаря СВОЙ — инкрементальная выборка Google выдаётся на календарь, и один общий курсор означал бы, что чтение второго сбрасывает позицию первого. Колонки `calendar_id`/`sync_token` у аккаунта остались от версии «один календарь»; `calendar_id` теперь значит «куда отправлять наше».
- **Право записи перечитывается у Google на КАЖДОМ проходе** (`refreshAccess`), а не задаётся в панели. Доступ могут выдать или отобрать не спросив нас, и календарь, подключённый на чтение, обязан сам стать двусторонним в день выдачи права — иначе это чинилось бы только переподключением руками, о котором никто не вспомнит. Новый календарь заводится с `read_only = 1` до первого прохода: предположить обратное значило бы разрешить отправку туда, о чём мы ещё ничего не знаем. В список выбора попадают ВСЕ календари аккаунта (раньше сужалось до `minAccessRole: 'writer'`) — самый частый случай как раз чужой публичный календарь мероприятий, и отфильтровав такие, панель не оставляла человеку ни одного варианта и никак не объясняла, почему нужного календаря в списке нет.
- **События слоя `gcal` — зеркало: их не правит НИКТО**, включая того, от чьего имени идёт импорт (он владелец лишь потому, что `owner_id` не может быть пустым). Запрет на сервере (`editableEvent` в `routes/calendar.js`), не только в интерфейсе. Причина не в правах, а в бессмысленности: правка не уехала бы обратно и вдобавок пропала бы сама при следующем обмене. По той же причине в конфликте «правили с обеих сторон» для read-only календаря чужая правка побеждает ВСЕГДА — иначе наша заморозила бы событие в состоянии, которого на той стороне нет.
- **Удаление события из read-only календаря надгробия НЕ пишет.** Копить их в расчёте на будущее право записи нельзя: в день его выдачи они разъехались бы разом и снесли бы у владельца события, которые никто не собирался удалять оттуда — у нас в тот момент это значило «убрать из зеркала», а не «удалить у всех».
- Цвет события дополнительного календаря — цвет СЛОЯ, а не тот, что стоит у события в Google: слой узнаётся в сетке именно по цвету, и разноцветные мероприятия внутри него сделали бы его неотличимым от остальных. У основного цвет берётся от самого события.
- Отключение дополнительного календаря удаляет его события: они были зеркалом, править их нельзя, и без источника они превратились бы в неудаляемый мусор. То же делает отключение аккаунта целиком (`disconnect`).
- Названия и цвета слоёв едут клиенту ВМЕСТЕ с событиями (`google_calendars` в `/api/calendar/events`), а не отдельной ручкой: слой без имени показать нечем, а вторым запросом список приезжал бы позже событий и слой моргал бы безымянным. Подключённый календарь показывается в панели слоёв даже пустым — в открытом месяце мероприятий может не быть вовсе, а слой, пропадающий вместе с ними, читается как «отключился сам».
- **Токены лежат зашифрованными** (AES-256-GCM, `googleOAuth.js`): `refresh_token` — это бессрочный доступ к чужому гугл-аккаунту, а файл базы целиком уезжает в бэкапы. Ключ — `GOOGLE_TOKEN_KEY`, при её отсутствии `JWT_SECRET`: заводить ещё один ОБЯЗАТЕЛЬНЫЙ секрет значило бы уронить сервер там, где раньше он поднимался. Не расшифровалось (сменили секрет, подсунули чужую базу) — это «аккаунт не подключён», а не падение. `client_secret` шифруется тем же способом и НАРУЖУ НЕ ОТДАЁТСЯ НИКОГДА — только признак `has_secret`; поэтому пустое поле секрета в форме значит «не меняли», стереть можно лишь явным `null`.
- Адрес возврата (`GET /api/calendar/google/callback`) — единственная ручка БЕЗ `verifySuperAdmin`, и иначе быть не может: туда браузер приводит сам Google, никаких наших заголовков там нет. Доказательство того, что код авторизации запросили из панели, ровно одно — одноразовый `state` (живёт 10 минут в памяти, гасится при разборе). Роутер монтируется РАНЬШЕ `/api/calendar`, у которого своя проверка токена. `access_type=offline` + `prompt=consent` обязательны: без `consent` Google второй раз `refresh_token` не пришлёт, и после первого же истечения часового токена синхронизация встала бы намертво.
- **Порядок внутри прохода — сначала отправка, потом чтение.** Наоборот было бы хуже: только что прочитанное мы бы тут же отправили обратно как «изменённое у нас», и каждая правка гуляла бы по кругу. Эхо собственной отправки отсекается парой `remote_updated_at`/`local_synced_at` в `google_calendar_links` — без них двусторонняя синхронизация зациклилась бы. Конфликт (правили с обеих сторон) решается в пользу более позднего изменения.
- **Удаление события пишет надгробие** (`google_calendar_deletions`) ДО удаления строки: привязка уходит по каскаду вместе с событием, и после удаления отправлять в гугл было бы уже нечего. Разносит надгробия следующий проход — держать сеть внутри обработчика запроса нельзя. Снимается надгробие только после успеха.
- **Правило повтора, которое наша модель не выражает, помечается `push_blocked = 1` и обратно НЕ отправляется никогда.** Наше правило — ровно `{freq, interval, until}`, а RRULE умеет «второй вторник месяца». Такое событие мы читаем приближённо (иначе оно вообще не показалось бы), но отправить его назад значило бы переписать в чужом календаре настоящее правило нашим упрощением. При этом избыточные `BYDAY`/`BYMONTHDAY`/`BYMONTH`, совпадающие с днём самого события, переводимости НЕ ломают: Google дописывает их к обычным правилам, и считать их непереводимыми значило бы записать в «только чтение» половину нормальных еженедельных встреч.
- `singleEvents` НЕ включаем: нужны сами серии с их RRULE, а не развёрнутые вхождения — разворачиванием занимается наш `calendarEvents.js`, и тысяча строк вместо одной серии сломала бы и его, и хранение. Отдельные вхождения (перенос, отмена) ложатся на `calendar_event_exceptions` по ключу `originalStartTime`, то есть по МЕСТУ вхождения в серии, а не по его новому времени. Разбор страницы идёт в два прохода — сначала серии, потом вхождения: порядок в ответе Google не обещан, и на первой же новой серии её правка потерялась бы, не найдя привязки.
- **`UNTIL` и `EXDATE` разбирают даты ПО-РАЗНОМУ, и это не мелочь.** Дата без времени в `UNTIL` — это «весь день включительно», то есть конец дня, иначе последнее вхождение серии срезалось бы как «позже предела». Та же дата в `EXDATE` указывает на само вхождение, а оно стоит на НАЧАЛЕ дня (`moscowInstant(dayKey, minutes)` в `calendarEvents.js`) — взяв конец дня, мы не попали бы ключом ни в одно исключение, и пропуск потерялся бы молча. Отсюда общий `parseStamp(raw, dayMinutes)` с явным параметром вместо одной функции на оба случая.
- Событие на весь день у нас — от полуночи до 23:59 последнего дня, а у Google — полуоткрытый интервал дат, где `end.date` в событие УЖЕ НЕ ВХОДИТ. Отсюда +1 день при отправке и −1 при чтении: без этого однодневное событие уезжало бы нулевой длины и пропадало из сетки.
- Своё событие узнаётся в гугле по метке `extendedProperties.private.nbrtEventId`. Нужна не для синхронизации (для неё есть таблица привязок), а для восстановления связи: подняли базу из бэкапа — привязки старые, а события в гугле те же, и без метки мы завели бы второй экземпляр каждого своего события.
- Импортированному событию нужен автор из `users` (`calendar_events.owner_id` — внешний ключ), а супер-админ панели — ОТДЕЛЬНАЯ сущность (`super_admins`), и его id туда не подставить. Поэтому в панели выбирается «автор импортированных событий»; без него синхронизация просто не идёт.
- Проход — раз в 5 минут (`googleCalendarSync.start`, первый отложен на 30 с после запуска: упираться в чужую сеть прямо на старте незачем). Состояние целиком в базе, включая курсор `sync_token`: перезапуск pm2 случается при каждой выкладке, и всё, что жило бы в памяти, терялось бы вместе с ним. Ответ 410 от Google — это «курсор протух», штатный случай: проход начинается заново без курсора, а не считается поломкой. По завершении шлётся широковещательный сокет-сигнал `calendar_changed` (общий календарь один на всех, персонализации нет), клиент по нему поднимает `calendarChangeToken` и перечитывает диапазон — иначе импортированное появлялось бы только после перелистывания месяца.
- Адрес возврата на проде: `https://cagrizzz.ru/miraschat/api/calendar/google/callback` — он должен быть вписан в «Authorized redirect URIs» приложения OAuth в консоли Google Cloud ДОСЛОВНО, иначе окно согласия отвечает невнятным `redirect_uri_mismatch`.

**Адаптивная раскладка (рефакторинг UI, 14.08.2026)**
- **Режим приложения — ОДНО вычисляемое значение на всё приложение** (`utils/layoutMode.ts`, чистая функция `resolveLayout` + хук `useLayoutMode`): `FULL → STANDARD → COMPACT → MOBILE`. Раньше список чатов переключался одним медиазапросом, панель ветки другим, и между ними существовали состояния, которых никто не проектировал, — например ветка, наехавшая поверх переписки на 761–1050px. Прежний `useNarrowLayout` удалён, `narrowLayout` теперь это просто `mode === 'mobile'`.
- **Переход наступает не на «красивом» разрешении, а когда набор областей перестаёт помещаться со своими минимумами.** Расчёт принимает фактическую ширину списка: у растянувшего список до 500px переход наступит раньше, и это правильно — он сам распорядился местом.
- **Порядок уступок жёсткий**: сначала закрывается правая область (ветка/сведения/файлы), потом список сжимается в иконки, потом мобильный режим. Переписка НЕ ужимается ниже `chatMin` ни на одном шаге — закреплено тестом, который проходит все ширины от 761 до 2200.
- **`chatMin = 520` — число не произвольное.** Это и нижняя граница удобного чтения (пузырь 70% → ~364px, 45–50 знаков), и ровно то значение, при котором у COMPACT появляется собственная полоса: полный список перестаёт помещаться на 852px, а мобильный начинается с 760px. Возьми меньше 428 — и режим «рельс + иконки + переписка» стал бы недостижим сужением окна, приложение проскакивало бы сразу в мобильный (поймано тестом при первом же прогоне).
- **Панели сначала ужимаются, и только потом меняется структура.** Перед закрытием правой области место у неё забирает список (до своего минимума 240): иначе на очень частой ширине 1280 ветка закрывалась бы «на два пикселя», хотя достаточно сузить список с 320 до 240. Формула в CSS-гриде (`--roster-actual`) обязана совпадать с формулой в `layoutMode.ts` — разойдись они, грид переполнит контейнер.
- **Дискретное считает JS, непрерывное — CSS.** React перерисовывается ТОЛЬКО при смене режима/компактности/видимости правой области (сравнение в `useLayoutMode`), а сколько именно пикселей достаётся списку и переписке, решает грид. Перерисовывать `Chat.tsx` на каждый пиксель перетаскивания рамки значит заставить окно ехать за курсором. По той же причине в хуке НЕТ `requestAnimationFrame`: троттлить нечего (функция чистая, сравнение дешёвое), а rAF не выполняется, пока окно не отрисовывается, — приложение возвращалось бы с раскладкой от прошлого размера.
- **`activeThread` — намерение, `layout.rightPanelOpen` — возможность.** Разделять обязательно: закрытую из-за нехватки места ветку надо вернуть саму при расширении окна, а закрытую человеком — не возвращать никогда. Рисовать панель при этом можно ТОЛЬКО по `threadPaneOpen`: колонки под неё в гриде нет, и панель складывалась в 92px поверх рельса (поймано при проверке).
- **Компактный список — тот же `ChatList` с флагом `compact`, а не второй компонент.** Прячется только то, чему нужна ширина (имена, превью, время, действия, поиск); остаются аватар, отметка выбранного и счётчики. `.row-body` не скрывается целиком, а выводится из потока: у строки «Ветки» счётчик лежит внутри неё, и `display:none` убирал бы индикатор, который обязан остаться (поймано при проверке).
- **`uiPrefs.rosterCollapsed` — три значения, не булево**: `true`/`false` — человек высказался, `null` — распоряжается адаптив. «Свёрнут сейчас» и «человек велел свернуть» — разные вещи, и путать их значит либо разворачивать список против воли при расширении окна, либо не сворачивать его, когда места нет. Ручное перетаскивание границы за минимум (с запасом 40px) сворачивает список и записывает это как решение человека.
- MOBILE переиспользует настоящий мобильный UI: рельс становится нижней панелью, ветка — отдельным экраном. Это работает медиазапросом `max-width: 760px` по ширине ОКНА, поэтому в узком окне Windows-клиента включается тот же мобильный интерфейс без единой копии компонентов. `MOBILE_MAX_WIDTH` в `layoutMode.ts` обязан совпадать с этим медиазапросом.
- **Проверять раскладку в браузерной панели можно только с ручной отправкой `resize`**: `resize_window` меняет viewport, но события `resize` не порождает, и состояние остаётся от прошлой ширины. Не баг приложения — свойство среды, как и неработающие там `requestAnimationFrame`/`ResizeObserver`/`loading=lazy`.

**Стикеры (feature/stickers, 14.08.2026)**
- **Стикер — САМОСТОЯТЕЛЬНЫЙ ТИП СООБЩЕНИЯ, а не вложение.** По требованию у него НЕТ ни просмотрщика, ни увеличения, ни какого-либо интерфейса медиа: в ленте это `<img class="bubble-sticker">` БЕЗ обёртки в `<button>` и без `onClick` вовсе — тап ведёт себя как тап по тексту. Обернуть его кнопкой, как картинку, значило бы получить фокусируемый элемент, который ещё и глотает жест. Контекстное меню — то же самое, что у текстового сообщения; «Копировать» и «Создать задачу» отпадают сами (они гейтятся по `msg.text`, которого у стикера нет), «Изменить» отключено явно.
- **В сообщении хранится ССЫЛКА на элемент пака (`messages.sticker_id`), а не путь к файлу** — решение пользователя, как у смайликов: картинка резолвится на лету через `GET /api/stickers/catalog`. Цена решения закрыта `messages.sticker_fallback` — копией эмодзи стикера НА МОМЕНТ ОТПРАВКИ. В отличие от смайлика, стикер не может деградировать до текста (`:code:` в тексте нет), поэтому при удалении стикера в админке на его месте показывается этот глиф того же размера (144×144), а не пустота. Проверено вживую: удаление стикера, уже отправленного в чат, оставляет 🐱 на прежнем месте, лента не дёргается.
- **Каталог отрисовки ≠ каталог выбора**, ровно как у смайликов: `GET /api/stickers` — только `enabled` паки без `retired` (пикер), `GET /api/stickers/catalog` — ВСЕ элементы независимо от `enabled`/`retired` (рендер старых сообщений). Выключение пака не должно оставлять в переписке дыры.
- **Эмодзи у стикера обязателен** (`sticker_items.emoji`, NOT NULL) — это и метаданные под будущий подбор стикеров по эмодзи, и тот самый fallback-глиф. Загрузка без эмодзи отклоняется (400). При загрузке НАБОРОМ ставится заготовка 🙂: спрашивать эмодзи на каждый файл из полусотни — это полсотни диалогов, поменять их удобнее в сетке.
- **У обычного пользователя НЕТ навигации по пакам** — он открывает вкладку и видит единый список всего доступного (`StickerPicker` склеивает `packs.flatMap(p => p.items)`). Паки существуют в модели данных и в админке; порядок, заданный там перетаскиванием, задаёт порядок и здесь.
- **Пикер стал общим: «Эмодзи / Стикеры / GIF»** (`ContentPicker`). Корневой контейнер, закрытие по клику мимо и высота мобильной панели живут в НЁМ, а вкладки получают `embedded` — иначе вышло бы несколько вложенных контейнеров, каждый со своим обработчиком закрытия, и панель захлопывалась бы от собственного клика. Вкладка GIF — заглушка «Скоро» (источника контента пока нет), но место в раскладке занимает сразу, чтобы не появляться задним числом и не сдвигать остальные.
- **Отправка стикера — сразу тапом в пикере**, без прикрепления к полю ввода: это самостоятельное сообщение, и «выбрать, потом нажать отправить» превратило бы один жест в три. Идёт через ту же `outgoingQueue` (`payload.stickerId` рядом с `filePath`), поэтому pending/failed/повтор/отмена работают без единой лишней строки. В ветке очереди нет — там `sendSticker` шлёт `thread_message` напрямую.
- **Стикер исключает текст и картинку** на сервере (оба обработчика, `chat_message` и `thread_message`): при `stickerId` финальный текст принудительно пустой, чтобы случайно прицепленная подпись не осела рядом в БД. Guard пустого сообщения расширен до `!finalText && !filePath && !stickerId`.
- **Админка — три ЭКРАНА, а не аккордеон** (`components/StickerPacksPanel.tsx`, вкладка «Стикеры»): список наборов → просмотр набора → редактирование. У стикеров есть обложка и обязательный эмодзи у каждого элемента, и в раскрывающуюся секцию (как у смайликов) это не помещается, не превращая её в кашу. Отдельным файлом, потому что `SuperAdminApp.tsx` — уже двухтысячестрочный монолит.
- **Перетаскивание вынесено в общий хук `utils/useDragReorder.ts`** — переезд логики из `EmojiItemGrid` без изменения поведения (те же 260 мс удержания для пальца, тот же не-пассивный `touchmove`, та же отмена по движению до таймера). Вторая копия этих восьмидесяти строк рядом со стикерами разъехалась бы с оригиналом на первой же правке. Поля ввода внутри плитки гасят `pointerdown` — иначе в них не поставить курсор.
- Удаление ПАКА переносит стикеры в служебный «Архив стикеров» (`retired = 1`, пак выключен и неудаляем) — та же механика, что у «Архива смайликов»: иначе исчезла бы отрисовка всех сообщений, которые на них ссылаются.
- **Проверять drag-and-drop и `onBlur` в браузерной панели нужно с оговорками**: `pointermove` и `pointerup`, отправленные в одном JS-кадре, React батчит, и коммит порядка видит СТАРЫЙ массив — события надо разносить по разным вызовам. А `onBlur` в React — это нативный `focusout`, а не `blur`: отправка `blur` не срабатывает вовсе. Оба — свойства среды/React, не баги приложения.

**Файлы, вложения переписки и откат версии (1.10.0, 14.08.2026)**
- **Файл — отдельные колонки `messages.document_path/_name/_size/_mime`, а не общий «attachment» с картинкой.** Картинка пережимается в webp и рисуется в ленте, файл сохраняется байт в байт и показывается карточкой со скачиванием — свести их в одну пару колонок значило бы на каждом шаге спрашивать «а это картинка?». `document_name` хранится отдельно от пути: на диск уезжает обеззараженное имя со случайной частью, человеку показывается исходное.
- **Имя файла из multipart приходит РАЗОБРАННЫМ КАК LATIN-1** — так устроен busboy под multer. «смета.pdf» превращалась в «ÑÐ¼ÐµÑ‚Ð°.pdf», и именно это видел получатель. Лечится `Buffer.from(name,'latin1').toString('utf8')` (`decodeMultipartName` в `routes/messages.js`); если результат содержит U+FFFD, оставляем исходную строку. Поймано тестом при первом же прогоне, на картинки не влияло только потому, что там имя не сохраняется.
- **Предел 50 МБ и текст отказа живут в двух местах намеренно** (`utils/fileLimits.ts` и `routes/messages.js`): серверная проверка обязательна (клиентскую обойти тривиально), клиентская нужна, чтобы человек не ждал загрузки 200 МБ ради отказа в конце. Текст по требованию говорит про тестовый режим, а не «файл слишком большой».
- **Вложения профиля («Медиа», «Файлы», «Ссылки») — отдельная ручка `GET /messages/:chatId/attachments?kind=`,** а не фильтрация уже загруженной истории: история грузится страницами по 50 сообщений, и «все картинки за три года» в ней просто нет. Удалённое и скрытое лично не попадают — те же правила, что в ленте.
- **Ссылки не хранятся отдельной таблицей.** Они и так лежат в тексте; отдельное хранилище пришлось бы наполнять миграцией по всему архиву и держать в согласии при каждой правке. Выборка сужается в SQL (`LIKE '%http%'`), разбор — в JS тем же способом, что при отрисовке. Дубли схлопываются: это справочник ссылок чата, а не лог отправок. Хвостовая пунктуация в адрес не входит.
- Вкладка «Голосовые» осталась выключенной заглушкой: механики нет вовсе, и пустой список был бы неотличим от «ничего не присылали».
- **Откат версии (`services/releases.js`, вкладка «Обновления») переписывает МАНИФЕСТЫ, а файлы сборок не трогает** — удалить сборку значило бы отрезать путь назад. sha512 и размер считаются с файла на диске, а не переносятся из старого манифеста.
- **Откат планируется целиком и только потом пишется.** Раньше запись шла по ходу проверок, и на первой же неудаче (у старой сборки неизвестен versionCode Android) откат обрывался ПОСЕРЕДИНЕ: `latest.yml` уже на старой версии, `android.json` ещё на новой, а админ видел ошибку и был уверен, что не произошло ничего. Поймано при первой живой проверке. Теперь неизвестный versionCode — не отказ, а пропуск ОДНОЙ платформы с явным отчётом (`skipped`).
- **versionCode Android хранится в реестре `releases.json`** рядом со сборками: из имени APK его не вывести, а разбирать бинарный AndroidManifest ради одного числа несоразмерно. Реестр пополняется на каждом чтении из действующего `android.json`.
- **`autoUpdater.allowDowngrade = true`** в `desktop/src/main.js` — без него откат до Windows-клиентов не доезжал бы вовсе: манифест уже на старой версии, а клиент считает себя новее и обновляться отказывается. **На Android откат работает только для НОВЫХ установок**: система запрещает ставить APK с меньшим versionCode поверх большего, и обойти это из приложения нельзя. В панели об этом сказано прямо.

**Личное хранилище, архивация вложений и вкладка «Файлы» (1.10.1, 15.08.2026)**
- **Всё, что принадлежит человеку, лежит под `uploads/users/<id>/`** (`services/userStorage.js`): `images/`, `files/`, `avatar/`, `wallpaper/`, `archive/`. Раньше загрузки лежали кучами по типам, и «сколько занимает этот сотрудник» или «убрать за уволившимся» решалось разбором ИМЁН файлов. Смайлики и стикеры НЕ переезжают — они общие для организации и ничьей личной собственностью не являются. Владелец — ОТПРАВИТЕЛЬ: пересланная копия ссылается на тот же файл, и раскладывать его дважды незачем.
- **Миграция идёт на КАЖДОМ старте сервера и идемпотентна** (`migrateLegacyUploads`): «выполнить один раз руками» — это то, о чём забывают при следующей выкладке. Порядок шагов обязателен: КОПИЯ → правка пути в БД → удаление исходника. При обратном порядке падение процесса посередине оставило бы строку, указывающую в пустоту, то есть картинку, пропавшую из переписки; при этом худший исход — лишний файл на диске, который уберёт следующий запуск. Владельца определяет ИМЯ файла (`msg_<id>_`, `doc_`, `user_`, `bg_`), а не строка в БД: одна картинка бывает в нескольких сообщениях, и владельцем должен остаться загрузивший. Файлы, на которые не ссылается ни одна строка, тоже раскладываются по владельцам — иначе старые каталоги не опустеют никогда. Старые пути (`/uploads/chat-images/...`) остаются ДОПУСТИМЫМИ при отправке: путь уже мог быть на руках у необновлённого клиента.
- **`MIRAS_UPLOADS_DIR` существует ради тестов, и это не перестраховка**: первый же прогон запустил миграцию по НАСТОЯЩИМ загрузкам с временной базой — файлы разъехались по личным папкам, а строки в рабочей базе остались со старыми путями. Тест, трогающий реальный `uploads/`, обязан задавать свой каталог.
- **Удаление вложения — это архивация в zip, а не стирание** (`services/attachmentArchive.js`): файл уезжает в `users/<id>/archive/<время>_<имя>.zip`, в сообщении заполняются `attachment_archived_at`/`attachment_archive_path`. Так выполняется и требование пользователя («на диске они переходят в zip»), и обязательство хранить переписку: содержимое остаётся на диске, только сжатым и вне живого дерева. Само сообщение НЕ помечается удалённым — текст, ответы и реакции на месте, пропадает только вложение. Внутри архива лежит имя, под которым файл отправляли, а не обеззараженное имя с диска. Обратной кнопки нет намеренно: «архивировать» должно звучать окончательно, иначе это ничем не отличается от «скрыть». Исходник удаляется, ТОЛЬКО если на него не ссылается другое неархивированное сообщение (пересылка).
- Право убрать вложение: отправитель — своё, орг-администрация — любое (тот же набор, что у `canDeleteForEveryone`). В чужом профиле у собеседникова файла пункта «Удалить» нет вовсе. Пропажа рассылается сокет-событием `attachment_archived` — иначе у остальных участников до перезагрузки чата висела бы битая картинка. Скрывать убранное обязаны ВСЕ выдачи: история, ветки, превью последнего сообщения, списки вложений и цитаты (`reply_to_archived`).
- **Категории вкладки «Файлы» считает СЕРВЕР** (`fileCategory` в `routes/messages.js`): документы / файлы / изображения / музыка. Раскладка нужна одинаковая в вебе, на телефоне и в десктопе, а три копии правил разъехались бы — человек видел бы файл то в «Документах», то в «Файлах» в зависимости от устройства. Расширение важнее MIME: телефоны сплошь и рядом шлют `application/octet-stream`. «Файлы» — честная категория (архивы, установщики), а не свалка «не разобрались».
- **Меню вложения открывается и тапом, и удержанием, и правым кликом.** Требование было сформулировано двумя пунктами сразу («при долгом нажатии» и «при нажатии»), поэтому открывают оба жеста, а первым пунктом у картинки стоит «Открыть» — просмотр никуда не делся. Флаг `longPressFired` гасит синтетический click после `touchend`: без него удержание открывало бы меню дважды и во второй раз не там.
- **Переход к сообщению из карточки вложений** — серверный параметр `?from=<id>` у истории: окно «от сообщения и до низа ленты», предел 500 сообщений. Постранично листать до него значило бы десяток запросов подряд; окно при этом оставляет НИЗ ленты загруженным, поэтому обычная прокрутка и подгрузка вверх продолжают работать. Сообщение дальше предела — `truncated: true` и честное сообщение человеку, а не лента с дырой. Три случая на клиенте: сообщение уже на экране (просто прокрутить), тот же чат (догрузить окно), другой чат (`pendingFocusRef` → загрузка истории окном при открытии).
- **Прокрутка к сообщению зависит от `messages`, а не только от id.** С фиксированной задержкой (60 мс) она молча не срабатывала: историю в этот момент подменяют окном на сотню строк, и `querySelector` не находил ничего (поймано живой проверкой — окно грузилось, подсветки не было). Теперь попытка повторяется на каждой перерисовке ленты, пока строка не появится.
- **Скачивание идёт ВНУТРИ приложения** (`utils/downloadFile.ts`): Electron — через главный процесс (`file:download`, сохранение в «Загрузки» с автонумерацией при совпадении имён), Android — СВОЙ нативный плагин `FileDownload` поверх системного DownloadManager, веб — blob + `<a download>`. Прежняя ссылка с `target="_blank"` уводила в СТОРОННИЙ браузер в десктопе (у нас внешние ссылки открывает `shell.openExternal`) и вовсе ничего не делала в Android WebView, который атрибут `download` не поддерживает. В вебе качаем через blob, а не прямой ссылкой: `download` действует только для своего origin, а API живёт на другом хосте. `downloadURL` в главном процессе принимает только http(s) — иначе рендерер мог бы попросить «скачать» любой файл с диска.
- **На Android @capacitor/filesystem для этого НЕ ГОДИТСЯ, и это стоило релиза** (1.10.1 → 1.10.2, 15.08.2026): плагин пишет файл обычным `java.io.File` в `Environment.getExternalStoragePublicDirectory(DOCUMENTS)`, а с Android 11 запись в общие каталоги так запрещена (scoped storage). Разрешения он при этом не спрашивает — считает, что на API 30+ оно не нужно, — то есть просто падает. Нажатие на файл не делало НИЧЕГО. Правильный путь — DownloadManager (`mobile/android/.../FileDownloadPlugin.java`, зарегистрирован в `MainActivity`): единственное место, куда приложению можно писать без разрешений, это «Загрузки»; попутно система сама показывает ход загрузки и уведомление о готовности. `WRITE_EXTERNAL_STORAGE` в манифесте стоит с `maxSdkVersion="28"` — на 10+ он не нужен и не запрашивается. Сам `@capacitor/filesystem` удалён из зависимостей: держать плагин, который для нашей задачи не работает, незачем.
- **Отказ скачивания ОБЯЗАН доходить до человека текстом** (`onNotice` из `ChatWindow` в баннер над лентой). Молчащая кнопка неотличима от сломанной: именно так выглядела запись, падавшая на Android, — результат `downloadFile` никто не читал, и жалоба звучала как «при нажатии ничего не происходит».
- **Ярлык на iPhone ставится только руками**: Safari не поддерживает ни кнопку установки, ни `beforeinstallprompt`. Поэтому метки `apple-mobile-web-app-*` в `index.html` (без них ярлык открывался бы вкладкой с адресной строкой) плюс подсказка `IosInstallHint` — она показывается ТОЛЬКО в Safari на iOS и только пока приложение не открыто с рабочего стола: в Chrome и Firefox на iOS пункта «На экран «Домой»» в меню нет, и советовать его там значит послать человека искать несуществующее. Закрытие запоминается в localStorage.

**Раздел «Файлы» — личное хранилище (1.10.3, 15.08.2026)**
- **Пункт рельса «Документы» переименован в «Файлы» и перестал быть заглушкой.** Идентификатор раздела оставлен прежним (`documents`): он лежит в сохранённом состоянии на устройстве у каждого, и переименование id разом сбросило бы всем открытый раздел.
- **Это НЕ вторая копия вкладки вложений из карточки чата.** Разница в том, зачем приходят: в карточке ищут файл конкретного собеседника (отбор по `chat_id`), в разделе распоряжаются СВОИМ из всех переписок сразу (отбор по `sender_id`, `GET /api/files`). Отсюда и разный состав: здесь поиск, сортировка, сводка занятого места, выбор нескольких файлов и массовое удаление — в карточке чата всего этого нет и не нужно.
- **Чужие файлы в раздел не попадают намеренно.** Распоряжаться (удалять) можно только своим, а «показать, но ничего не дать сделать» — это ровно тот список, который уже есть в карточке собеседника.
- **Картинки считаются файлами.** Они так же занимают место на диске, и «убрать за собой» человек приходит именно за ними. Различие только в показе (`kind: image` — есть превью) и в имени: у картинки в переписке имени нет, поэтому подставляется «Изображение от <дата>» — показывать `msg_39_1786…webp` бессмысленно.
- **Сводка занятого места честно разделена на две величины**: байты (только документы — у картинок в БД хранятся ширина и высота, а не размер) и счётчик картинок отдельно. Сложить их в один «объём» значило бы соврать. Полоса раскрашена по видам файлов: цифра в мегабайтах сама по себе ничего не говорит, важно, ЧТО занимает место.
- Удаление здесь — та же архивация в zip, что и везде (`POST /messages/:id/attachment/archive`), включая массовую: подтверждение прямо говорит, что файл пропадёт у всех участников, а на сервере уедет в архив. Архивные видны отдельной кнопкой «Архив · N», и у них в меню нет ни скачивания, ни удаления — только переход к сообщению и прямая подпись, что вернуть может администратор.
- **`fileCategory` вынесен в `server/utils/fileCategory.js`** — одна раскладка на раздел и на карточку чата. Вторая копия правил означала бы, что один и тот же файл попадает в разные категории в разных местах.
- **«Перейти к сообщению» переключает экран ВСЕГДА, а не только при смене чата.** Раньше, если чат уже был открыт, обработчик лишь ставил подсветку — а человек в этот момент смотрел на список файлов, и нажатие выглядело несработавшим. Поймано живой проверкой на узком экране, где раздел занимает весь экран целиком.
- Аккаунты «Интернет» раздел не видят (`INTERNET_VISIBLE_SECTIONS`) — как и раньше, когда он был заглушкой.

**Меню строки в списке чатов и разделение типов аккаунтов (1.10.4, 15.08.2026)**
- **Кнопки «закрепить» и «убрать из списка» со строки убраны, все действия — в контекстном меню строки** (правый клик, кнопка «⋯» по наведению, долгое удержание на телефоне): закрепить/открепить, пометить прочитанным, отключить/включить уведомления, очистить переписку, убрать из контактов. Состояние теперь показывают ЗНАЧКИ (булавка, перечёркнутый колокольчик), а не кнопки: строка перестала быть панелью управления и снова читается как строка.
- «Пометить прочитанным» показывается только при непрочитанном — пункт, который заведомо ничего не сделает, лучше не показывать вовсе. Отдельное сокет-событие `mark_chat_read` (а не общий `mark_all_read`): гонять проход по всей переписке ради одного чата незачем, правила отметки те же самые (личные — по `status`, общие и группы — по `message_reads`).
- **«Очистить переписку» — только личная переписка и «Избранное».** В группе и общем чате это чужая переписка для десятков человек, а у владельца группы для уборки есть свой массовый инструмент. Проверка на сервере (`POST /api/messages/:chatId/clear`), а не только в интерфейсе.
- **Очистка = то же мягкое удаление, что и у одного сообщения**: строки остаются в базе целиком (`deleted = 1`), ни `text`, ни `file_path`, ни файлы на диске не трогаются — обязательство хранить переписку действует и здесь. Наружу очищенное не отдаётся ни в истории, ни в превью списка чатов. Событие `chat_cleared` одно на весь чат, а не по сообщению на каждое: их бывают тысячи.
- **Разделение типов аккаунтов стало полным: исключения для администрации в справочнике БОЛЬШЕ НЕТ** (требование пользователя от 15.08.2026, отменяет прежнее правило про `ADMINISTRATION_SQL`). Ни орг-роль `admin`/`moderator`, ни группа «Админы» больше не дают видеть другую сторону. Одновременно оба типа видит только супер-админ в панели управления — у неё свой вход и своя выдача. **Следствие, о котором нужно помнить:** из самого приложения «Интернет» теперь не может написать администрации с просьбой сменить тип аккаунта — эта просьба должна дойти мимо мессенджера.
- Раздел «Файлы» аккаунтам «Интернет» доступен (`INTERNET_VISIBLE_SECTIONS`): своё хранилище есть у каждого, к разделению типов оно отношения не имеет.
- Предупреждение при удалении файла сокращено до одного вопроса («Удалить «имя»?») — по требованию пользователя: подробности про архив и участников читались как запугивание.

- **Список вложений хранится ВМЕСТЕ с видом, к которому относится** (`loaded = {kind, items}` в `ChatAttachments`). Раньше вкладка и список были двумя независимыми величинами, и между переключением и приходом ответа существовал кадр «вкладка уже Медиа, список ещё из Файлов»: плитка бралась за `file_path`, которого у файла нет, и приложение падало на `undefined.split('/')`. Падало ТОЛЬКО там, где во вкладке «Файлы» что-то лежит, — отсюда жалоба «падает на одном конкретном человеке» (1.10.3, Windows).
- Тест на это падение обязан переключать вкладку ПОСЛЕ появления содержимого предыдущей: если щёлкать быстрее ответа сервера, `loading` не даёт наступить тому самому кадру, и тест зеленеет на сломанном коде (проверено — первая версия теста именно так и прошла).

- **Байты выбранной картинки читаются СРАЗУ при выборе, а не при отправке** (`stageFiles` в `MessageInput.tsx`). `File` — только ссылка на файл системы: между «прикрепил» и «отправил» проходят минуты, и Android успевает убрать временный файл камеры или «Поделиться», а снимок могут удалить из галереи. Чтение падало именно в момент отправки, человек видел «Файл удалён или недоступен» с уже набранной подписью, и воспроизвести это нарочно нельзя — зависит от чужого приложения и времени. Своя копия в памяти разрывает зависимость: после выбора отправка ни от чего снаружи не зависит. Нечитаемый уже при выборе файл объясняется сразу, а не после написания подписи.
- В тестах на прикрепление обязательны заглушки `URL.createObjectURL`/`revokeObjectURL` (jsdom их не реализует вовсе) и проверка копии по размеру и имени, а не по `arrayBuffer()` — его у `File` в jsdom тоже нет.

**Навигация, «Главная» и новый список чатов (1.10.6, 15.08.2026)**
- **Стартовый раздел приложения — «Главная», а не чаты.** Приложение перестаёт быть «списком переписок с довесками»: после запуска человек видит свою сводку, а чаты становятся одним из разделов. Раздел `home` объявлен первым в `SECTIONS` и стоит в `INTERNET_VISIBLE_SECTIONS` — сводка личная и к разделению типов аккаунтов отношения не имеет.
- **«Главная» — не витрина статистики: каждый блок это переход.** Число без адреса бессмысленно («18 непрочитанных» и что дальше?), поэтому у карточки всегда есть, куда она ведёт. Блоки независимы (свой источник, своё состояние загрузки) — дальше сюда добавляются упоминания, важные сообщения, закреплённое, пространства, и добавление блока не должно означать переписывание экрана. Счётчики берутся из ТЕХ ЖЕ ручек, которыми живут сами разделы (`/tasks`, `fetchRange` календаря, непрочитанное — пропом из `Chat.tsx`): отдельная серверная сводка означала бы вторую копию правил видимости календаря, которая неизбежно разъедется с первой.
- **«Люди» переименованы в «Контакты»**, набор разделов один на обе раскладки. На узком экране показываются шесть (`MOBILE_SECTIONS`: главная, задачи, календарь, контакты, чаты, настройки) — предел, за которым подписи налезают друг на друга на 360px; «Пространства» и «Файлы» остаются на десктопном рельсе. Прежний вход в настройки из шапки списка чатов убран вместе с `roster-settings-btn`: раздел теперь есть в самой панели.
- **Нижняя панель — «островок»**: отступы 8px от краёв, скругление, тень, `env(safe-area-inset-bottom)` под жестовую полосу. Это ОФОРМЛЕНИЕ, а не всплывающий элемент: панель постоянна и остаётся основной навигацией. Раз она парит над содержимым, место под неё резервируется вручную (`padding-bottom` у `.roster-list` и `.section-host`) — иначе последняя строка списка оказывается под панелью.
- **Правая часть строки чата: плашка «булавка + время», под ней галочки и счётчик.** Закрепление объединено с датой в один элемент — признак читается сразу, но лишней колонки в строке не появляется. Галочки — то же состояние сообщения, что и в переписке (`status` из превью), и только у СВОЕГО последнего сообщения: у чужого статус относится к чтению собеседником и в списке ничего не значит. Кнопка «⋮» из строки убрана целиком, меню открывается правым кликом и удержанием.
- **Значок «уведомления отключены» — у ИМЕНИ чата, а не в правой колонке**: справа уже время, галочки и счётчик, и признак «этот чат молчит» среди них терялся.
- **Миниатюра последнего сообщения** — часть превью перед текстом (18×18, `object-fit: cover`), высоту строки не растит.
- **`/meta/last` отдаёт последнее СУЩЕСТВУЮЩЕЕ сообщение.** Раньше бралось последнее вообще, и если его удалили, чат в списке выглядел пустым, хотя выше лежит нормальная переписка. Теперь удалённое и скрытое лично пропускаются, а вместе с текстом приезжают `sender_id`/`sender_name`/`status` (для галочек и подписи автора в группах) и размеры картинки (для миниатюры). Следствие: у полностью очищенного чата превью нет вовсе — это правильное состояние, и тест на очистку проверяет именно его.
- **Фильтры «Все чаты · Личные · Группы · Новостные» — фильтрация ОДНОГО списка**, а не отдельные экраны: порядок, закрепления и счётчики те же. «Новостные» — то, что читают, а не обсуждают: каналы-объявления (`announcements_only`) и общий чат, подписанный как рассылка на всю организацию. Строка «Ветки» показывается только в «Все чаты»: это не чат и ни под один фильтр не подходит.
- **«Мой статус» — отдельный блок над списком, а не первый чат** и не аватар в шапке (шапка со сменой навигации освободилась). Показывает статус и срок («до 19:00»), по нажатию открывает выбор статуса.

**Правки навигации и мелочей интерфейса (1.10.7, 15.08.2026)**
- **«Главная» открывается только при ПЕРВОМ запуске за день** (`lastHomeDay` в localStorage). Сводка нужна утром — увидеть, что накопилось; на десятый запуск за день она мешает: человек открывает приложение ради переписки. Дата хранится на устройстве: синхронизировать её между устройствами незачем.
- **Разделы занимают весь экран, панель парит НАД ними.** Было `inset: 0 0 58px` у `.roster`/`.conversation`/`.section-host` — и под панелью оставалась мёртвая полоса фона (та самая «пустота» на чатах, календаре и настройках). Запас, чтобы поднять последний элемент над панелью, дают только ПРОКРУЧИВАЕМЫЕ области (`padding-bottom`), а не контейнеры: у флекс-контейнера padding не прокручивается, он просто съедает высоту.
- **Поиск возвращается ОТТЯЖКОЙ, а не сам.** Раньше он появлялся, стоило списку доехать до верха, и на каждом возврате наверх экран дёргался под пальцем. Теперь у верхнего края нужно ещё потянуть вниз (56px) — это отдельное намерение «хочу поиск». Прятаться при прокрутке вниз он продолжает сам.
- **Отклик на бесполезные жесты** (`utils/useEdgeFeedback.ts`): упор в край списка отвечает мягким смещением с возвратом. Появляется ТОЛЬКО там, где действие невозможно, и гаснет само — постоянное подрагивание раздражало бы сильнее, чем отсутствие ответа. Величину оттяжки считает JS, возврат делает CSS-переход.
- **Смахивание влево-вправо переключает вкладку** (`utils/useSwipeSections.ts`) — только на узком экране и только когда открыт сам раздел, а не переписка поверх него: там жест занят выделением сообщений. Не срабатывает внутри того, что листается само (лента недавних, чипы фильтров, календарь, композер, поля ввода). На краях панели ничего не происходит: заворачивать по кругу значит одним движением уводить с «Главной» в «Настройки».
- **Удержание в списке чатов больше не срывается.** Отмена жеста шла на ЛЮБОЙ `touchmove`, а Android шлёт его от дрожания неподвижного пальца — меню открывалось через раз. Теперь отменяет только реальное движение (10px). Вдобавок в списке полностью отключено выделение текста (`user-select: none`): удержание — это вход в меню, а браузер на тот же жест начинал выделять текст, показывая своё меню поверх нашего и «лупу» на Android.
- **Контекстное меню на открытом изображении**: сохранить, ответить, поделиться, копировать, удалить из кэша, удалить. Открывается правым кликом и кнопкой (на телефоне правого клика нет, а удержание там занято перетаскиванием увеличенной картинки). «Копировать» перерисовывает картинку в PNG — буфер обмена браузера других форматов не принимает, и webp из переписки молча не копировался бы. «Удалить из кэша» чистит ровно этот адрес, а не весь кэш. «Ответить» и «Удалить» ведут в те же обработчики, что и меню сообщения: своей логики просмотрщик не заводит.
- **Аппаратный «Назад» снимает выделение сообщений** через ту же цепочку перехватчиков, что и оверлеи (`backInterceptors`). Раньше Back уводил с экрана целиком — вместе с выбором и местом в переписке.
- **Окно статуса**: пресеты, свой текст со СВОИМ эмодзи и срок — либо длительностью, либо конкретным временем («до 19:00»). Время побеждает длительность: его указали явно и последним. Прошедшее время значит завтра — иначе «до 9:00», выставленное вечером, сняло бы статус мгновенно. Эмодзи выбирается из общего набора приложения; картиночный смайлик подставляется своим базовым юникодным символом, потому что статус живёт ТЕКСТОМ в десятке мест. Хранится он первым символом `status_custom`, а не отдельной колонкой — новое поле пришлось бы протаскивать во все эти места; разбирает обратно `describeStatus`.
- **Фото профиля группы ставит владелец** (`chat_groups.avatar_path`, `POST /api/groups/:id/avatar`). Файл ложится в личную папку загрузившего: своей папки у группы нет, а владелец есть всегда. Прежний файл удаляется — на аватар группы, в отличие от картинок в переписке, не ссылается ни одно сообщение. Участникам изменение приезжает тем же `group_updated`, что и переименование.

**Контракты данных**
- `CalendarOccurrence`, `EventDraft`, слои календаря (`global`/`personal`/`birthdays`/`space:<id>`/`gcal:<id>` — последний это зеркало дополнительного календаря Google, только на чтение).
- Группа: `{id, chat_id, name, created_by, created_at, member_count, role, members[], announcements_only}` — см. `server/routes/groups.js`.
- Стикер: `sticker_packs {id, name, cover_path, position, enabled}` + `sticker_items {id, pack_id, file_path, animated_path, emoji, position, retired}`; в сообщении — `messages.sticker_id` + `messages.sticker_fallback`. См. `server/routes/stickers.js`.
- Очистка переписки: `POST /api/messages/:chatId/clear` (только `chat_a_b` и «Избранное»), сокет-событие `chat_cleared`; отметка одного чата прочитанным — сокет-событие `mark_chat_read`.
- Личное хранилище: `GET /api/files?category=&search=&sort=new|old|big|name&archived=0|1` и `GET /api/files/summary`.
- Файл в сообщении: `{document_path, document_name, document_size, document_mime}` + `attachment_archived_at`/`attachment_archive_path` у убранного; вложения переписки — `GET /api/messages/:chatId/attachments?kind=media|files|links` (у файлов ещё `category`: documents|files|images|music). Архивация — `POST /api/messages/:messageId/attachment/archive`. Окно истории от сообщения — `GET /api/messages/:chatId?from=<id>`.
- Задача: `{id, title, description, status, due_at, created_by, participants[], can_edit, archived}` — см. `server/routes/tasks.js`. `status` — `not_started`/`in_progress`/`done`.
- Статус профиля: `users.status_preset` (пресет из фиксированного набора) + `users.status_custom` (свой текст) — взаимоисключающие, см. `utils/statusMeta.ts`.
- Плейсхолдер поля ввода при статусе собеседника — формат «Сообщение {Имя} {эмодзи} {статус}». Имя тут повторяется намеренно, хотя оно есть и в шапке над полем: раньше требование было обратным («убрать имя»), 5 августа 2026 пользователь развернул его и проверяет новый формат на живых людях. Не «чинить» обратно.

- Область удаления сообщения: `forEveryone` в сокет-событии `message_delete`. Без него — персональное скрытие (таблица `message_hidden`, per-user), сообщение убирается только у того, кто удаляет; с ним — `deleted=1`, у всех. Право убрать у всех (`canDeleteForEveryone` в `index.js`): своё — всегда, чужое в личной переписке — любому из двоих, чужое в группе/общем чате — только владельцу группы или орг-администрации (`users.role` admin/moderator). Тот же набор прав у REST-ручки массового удаления (`requireGroupCleaner` в `routes/groups.js`). Скрытое фильтруется из истории, превью последнего сообщения и счётчиков непрочитанного — везде через `NOT EXISTS ... message_hidden`, а не в JS после выборки (иначе страница пагинации приезжала бы короче лимита, а `hasMore` врал).
- **Реакции и «Ответить» — ОДНА строка под пузырём (`.msg-underrow`), а не две.** Обе относятся к одному сообщению, и разложенные по разным строкам они занимали двойную высоту, а реакции отрывались от пузыря. Наезд на пузырь (`margin-top: -2px`) и `z-index: 1` переехали с `.msg-reactions` на саму строку — без z-index фон пузыря съедал бы верхнюю кромку плашек. У `.thread-link` снят `align-self: stretch`: растянутая на всю ширину кнопка выдавливала бы реакции на отдельную строку и возвращала ровно то разделение, ради устранения которого их и свели. `flex-wrap` оставлен — при десятке реакций кнопка ветки уезжает вниз, а не выталкивает их за край. Прежняя заметка «порядок: реакции, потом Ответить» этим отменена: порядок больше не решает, оба в одном ряду. Ранее у `.thread-link` был убран `min-height: 32px` — у короткой кнопки без аватаров текст центрировался внутри этой высоты, и сверху набегало вдвое больше воздуха, чем в `margin`.
- **Время у картинки без подписи — плашкой НА кадре, как в Telegram** (`.bubble-meta.is-on-image`), а под ней полоска пузыря снимается (`.bubble-has-image-meta .bubble-image { margin-bottom: -7px }`). Раньше ради одной строчки времени под каждым снимком висела полоса цвета пузыря и читалась как рамка. Цвет плашки СВОЙ (белое по затемнению), а не `var(--meta-*)`: под ней произвольная фотография, и тема о её яркости ничего не знает. У «голого» кадра (над ним в пузыре нет ни имени автора, ни пересылки, ни цитаты) пузырь убирается целиком — `.bubble-bare-image { padding: 0 }`. **Ширину такой картинке обязан задавать инлайн-стиль из `file_width`, а не проценты**: в пузыре без полей картинка осталась его единственным содержимым, и процентная ширина считалась бы от пузыря, который сам ждёт ширины от неё, — оба схлопывались в ноль (поймано при проверке). Поэтому `bareImage` требует наличия `file_width`/`file_height`; своя, ещё не отправленная картинка размеров не имеет и рисуется прежним способом.
- Закрепление чата: в интерфейсе «Закрепить»/«Открепить» с иконкой булавки, но ручки и таблица на сервере по-прежнему `favorites` — переименована только видимая человеку часть. Причина: рядом в списке есть личный чат «Избранное» (`self_<id>`, куда пересылают сообщения), и звезда «в избранное» читалась как отправка туда. Закреплённые идут первыми в общем списке (ранг `-2` в `groupRank`, выше общего чата) и БЕЗ заголовка раздела: они не отдельная группа, а те же чаты, поднятые наверх.
- Реакции: `message_reactions` с PRIMARY KEY `(message_id, user_id)` — это и есть правило «одна реакция на человека», повторная установка идёт через `ON CONFLICT DO UPDATE` и заменяет прежнюю; повторный клик по своей же снимает. Снять чужую может только автор сообщения и только под своим (`reaction_remove` в `index.js`). Базовый набор — `app_settings.reaction_emoji`, правится в панели (вкладка «Реакции»), приезжает клиенту в `/users/me`; уже поставленные реакции сменой набора не затрагиваются. Рисуются под пузырём с аватаром поставившего (по спеке, не «эмодзи+счётчик»); снятие: крестик по наведению на ПК, долгое удержание по самой реакции на Android.
- Контекстное меню сообщения собирается списком (`buildMenuItems` в `ChatWindow.tsx`), а не гирляндой `&&` в разметке: состав и ПОРЯДОК различаются для ПК/Android и своего/чужого сообщения, по месту за этим не уследить. Отметки «Прочитано в …»/«Изменено в …» — `kind: 'info'`, не кнопки. `messages.read_at` заполняется только в личной переписке (`readReceipts.js`): в группах время прочтения у каждого своё и живёт в `message_reads`, одной метки на сообщение там не существует.
- Меню умеет прокручиваться внутри себя (`max-height` + `overflow-y`), а эффект подгонки позиции сравнивает вычисленные координаты с текущими и выходит, если они совпали. Без этого на низком окне высокое меню упиралось в `Math.max(4, …)`, overflow не исчезал, состояние переставлялось «на то же самое» — React рвал цикл ошибкой «Maximum update depth exceeded».
- **Кнопка отправки НЕ забирает фокус у поля ввода.** Была `type="submit"`, и тап по ней на Android переносил фокус на саму кнопку — contentEditable его терял, IME закрывалась, и каждое следующее сообщение подряд требовало нового тапа по полю (жалоба «клавиатура сразу закрывается»). Теперь `type="button"` + `onPointerDown` с `preventDefault()` и отправкой прямо оттуда — тем же приёмом, что давно работает у кнопки смайликов. `onClick` оставлен ради клавиатурной доступности на ПК и защищён отметкой времени (`pointerSubmitAtRef`, 700 мс): на touch `preventDefault` может съесть синтетический click, а на мыши он приходит всегда, и без отметки одно нажатие отправляло бы дважды.
- **Появление панели ответа само отдаёт фокус полю ввода** (эффект по `replying?.id` в `MessageInput`, через `requestAnimationFrame` — композер в этот момент ещё меняет высоту). Раньше после «Ответить» приходилось дополнительно кликать по полю. На мобильном фокус заодно поднимает клавиатуру обычным путём `handleMobileFieldFocus` — здесь это и требуется.
- **Лента доскручивается по `ResizeObserver` на самом контейнере, а не только по приходу сообщения.** Высоту ленты меняет не один источник: панель ответа над полем ввода, превью прикреплённой картинки, панель правки, поворот экрана. Каждый отъедал высоту уже ПОСЛЕ прокрутки к низу, и последнее сообщение уезжало под появившуюся панель (замерено: 602→546 px, низ уходил на 28 px). Событие `miras-composer-resize` покрывает только мобильную поверхность ввода и о них не знает. Докрутка идёт лишь при `shouldScrollRef.current` — чтение истории выше рвать нельзя. Отдельно `onLoad` у картинки сообщения: `ResizeObserver` этого не ловит вовсе, там растёт СОДЕРЖИМОЕ, а высота контейнера та же (актуально для своей, ещё не отправленной картинки — у неё нет `file_width`, а значит и `aspectRatio`).
- **Список голосов опроса обязан гасить весь ввод, а не только клик.** `PollCard` рисуется внутри пузыря, поэтому события его панели всплывают по React-дереву прямо в жесты строки `.msg`: тап по списку открывал контекстное меню сообщения ПОД панелью, удержание входило в режим выделения. Гасятся `touchstart/touchmove/touchend/pointerdown/mousedown/contextmenu`. Вынос в портал сам по себе НЕ помогает — React-события всплывают по дереву компонентов, а не по DOM. Панель также заведена в цепочку аппаратного Back (`registerBackInterceptor`).
- **Синтетический click после touchend — источник почти всех «само нажалось» на Android.** Браузер шлёт mouse-события с задержкой ~300 мс в ту же точку, где палец оторвался, а к этому моменту разметка там уже другая. Ловили трижды: тап открывал меню — и click приходился по пункту, оказавшемуся под пальцем (самопроизвольная пересылка); долгое удержание отмечало сообщение — и click тут же снимал отметку, режим выделения захлопывался; удержание снимало реакцию — и click проваливался на сообщение под исчезнувшей плашкой. Правило: если обработчик тача сам что-то сделал, он ОБЯЗАН вызвать `e.preventDefault()` на `touchend` и не рассчитывать на эмуляцию мыши — то, что должен был сделать тап, делается там же руками. И наоборот: если палец лёг на кнопку внутри строки (картинка, цитата, плашка реакции, галочка), жест не заводится вовсе — иначе `preventDefault` съел бы её собственный click и картинка перестала бы открываться.
- Жест на сообщении (Android, `ChatWindow.tsx`): тап открывает контекстное меню, долгое удержание (`LONG_PRESS_MS`) сразу входит в режим выделения (отмечая тронутое сообщение, без меню), протяжка после удержания тянет диапазон и добавляет его к уже отмеченному (`baseSelection` в жесте — иначе новая протяжка стирала бы прежний выбор). Обычное движение пальцем в режиме выделения остаётся прокруткой: иначе до сообщений за экраном было бы не добраться. На время протяжки прокрутка глушится своим не-пассивным слушателем `touchmove` на контейнере — React вешает `touchmove` пассивно (17+), `preventDefault` из его обработчика не работает вовсе. Любое движение пальца ДО срабатывания удержания — обычная прокрутка ленты: жест целиком отменяется, `preventDefault` нигде не вызывается, чтобы браузер продолжил скроллить и синтетический `click` после тапа не потерялся. Различают три исхода одним `touchGesture` ref (`moved`/`sweeping`), а не отдельными таймерами — на `touchend` по нему решают, был ли это тап (открыть меню) или уже шло выделение (открывать нечего, снятие/добавление идёт через `onClick` по строке). Явный отдельный `handleTouchCancel` — на настоящую отмену жеста (входящий звонок и т.п.) меню открывать нельзя, в отличие от `touchend`. Отдельной кнопки входа в выделение нет — только долгое удержание или пункт «Выделить» в меню; выход — либо явная отмена, либо автоматически, когда снята последняя галочка (`selectedIds.size === 0`).
- **Загруженные файлы отдаются с вечным кэшем** (`express.static` для `/api/uploads`: `maxAge: '365d', immutable`). По умолчанию там `max-age=0`, и браузер перепроверял КАЖДЫЙ смайлик, аватар и картинку при каждом открытии — ответ 304, но на слабой связи это круговой обход на файл. Именно этим группа открывалась медленнее личного чата: на сервере разница всего ~2 мс (замерено на 8 тыс. сообщений), а в группе под каждым сообщением аватар, и таких перепроверок десятки. `immutable` — не допущение, а свойство схемы имён: содержимое по одному пути не меняется никогда (`user_<id>_<время>.jpg`, `msg_<id>_<время>_<случайное>.webp`, `emoji_<имя>_<случайное>.webp`; замена картинки смайлика пишет НОВЫЙ файл). Заведёте загрузку с предсказуемым именем — правило придётся пересматривать.
- Картинки сообщений — `loading="lazy"`, и это безопасно только потому, что у обёртки задан `aspectRatio` из сохранённых `file_width`/`file_height`: место под картинку известно до её прихода, лента не дёргается и автопрокрутка вниз не промахивается. Проверять lazy в панели предпросмотра бесполезно: при `document.visibilityState === 'hidden'` пересечение с областью видимости не вычисляется и картинки не грузятся вовсе — это среда, а не баг.
- Картиночный смайлик до загрузки держит место базовым эмодзи (`.custom-emoji-fallback.is-placeholder`), тем же, что подставляется при пропавшем файле. Заглушке нужен `overflow: hidden`: у inline-block с видимым содержимым базовая линия берётся от последней строки ТЕКСТА, а у картинки — от нижнего края, из-за чего заглушка вставала на 9px ниже и подмена дёргала строку. Размеры совпадают до пикселя (29×29 при 2em), `font-size: inherit` обязателен — иначе `2em` считались бы от кегля самой заглушки. Уже показанные пути помнит `loadedEmojiPaths`, чтобы на перерисовках смайлик не моргал заглушкой повторно.
- Картинка в пузыре: `.bubble-image:not(:first-child)` — правило намеренно по «не первый ребёнок», а не по конкретному соседу. Отрицательный верхний отступ (картинка в край пузыря) верен, только когда над ней ничего нет; на имени автора этот баг ловили один раз, на «Переслано от» — второй.
- Все модалки делят один `z-index` — при равном порядок в DOM решает, кто сверху, а не то, какое окно открыли позже. Профиль (`UserInfoModal.tsx`) можно открыть поверх уже открытого окна («Люди»): у него отдельный класс `.modal-overlay-nested` (z-index выше базового), иначе он рендерился бы под People, хотя открыт позже.
- **Режим окна под клавиатуру Android — общий ресурс со счётчиками** (`utils/mobileKeyboard.ts`): `acquireChatKeyboardResizeMode` держит overlay (`adjustNothing`, MessageInput сам двигает композер), `acquireStandardKeyboardResizeMode` перебивает его на штатный `adjustResize` и имеет приоритет. Прямые `setOverlay(true/false)` из каждого экрана конфликтовали: ветка монтирует ВТОРОЙ MessageInput поверх первого, и размонтирование одного выключало overlay у другого. **Любое окно с полем ввода, открытое ПОВЕРХ переписки, обязано брать `acquireStandardKeyboardResizeMode` на время своей жизни** — иначе WebView под клавиатуру не сжимается, а `.modal-overlay` растянут на `inset: 0`, и центрированная карточка остаётся по центру всего экрана, уходя нижней частью под IME (компенсации высоты клавиатуры у модалок нет). Уже берут: PollCreator, ForwardModal (поиск «Куда переслать» стоит внизу карточки), GroupInfoModal (переименование + поиск участников), UserInfoModal (комментарий). Окна, открываемые из списка чатов (справочник, создание группы, выбор статуса), не при чём — на узком экране переписка в это время вообще не отрисована, overlay никто не держит.
- **Аппаратный Back на Android разбирается цепочкой в `Chat.tsx`**, и каждый оверлей обязан в ней быть, иначе Back уводит экран из-под открытого окна, а окно остаётся висеть поверх уже другого экрана. Что не поднято в состояние `Chat.tsx` (просмотр картинки, список поставивших реакцию — они внутри `ChatWindow`), подписывается на `registerBackInterceptor` (`utils/backInterceptors.ts`); стек строго LIFO, снятие идёт по значению, а не `pop()` — нижний оверлей может закрыться раньше верхнего. `runTopBackInterceptor()` вызывается первым после `closeMobileInputSurface()`.
- Карточка общего чата — `GeneralChatInfoModal.tsx`, открывается из шапки переписки и по аватару в списке. **Списка участников там нет намеренно** (убран 12.08.2026) — это единственная группа, где состав не показывается: он совпадает со всей организацией, управлять им отсюда нельзя (участие в общем чате не выдаётся и не отбирается), и список был вторым справочником рядом с «Людьми». Остались счётчик и уведомления — единственная своя настройка чата. Счётчик по-прежнему считается из `/api/users`, а тот намеренно НЕ отдаёт самого спрашивающего (`u.id != ?`, он рассчитан на «кому написать»), поэтому себя надо прибавлять руками, иначе в чате всей организации счётчик занижен ровно на одного зрителя.
- Автофокус в поле при открытии окна — только на ПК (`AUTOFOCUS_ON_OPEN` в `utils/autoFocus.ts`, проверяет нативный мобильный и `pointer: coarse`). На телефоне он мгновенно выдвигает клавиатуру, а она закрывает то самое окно, которое человек открыл (в «Люди»/«Куда переслать» под ней пропадала вся выдача). Поля, куда человек зашёл осознанно (правка названия группы, заметки о человеке), фокусируются по-прежнему всегда — там клавиатура и нужна.
- Уведомления-тосты (`NotificationStack.tsx`) закрываются смахиванием вверх: `touchmove` двигает `transform: translateY` и гасит `opacity` по мере движения, порог `SWIPE_DISMISS_PX` на `touchend` решает — закрыть или откатить обратно. Во время протяжки `paused=true` (тот же флаг, что и при наведении мышью) — автоскрытие не должно погасить тост, пока за него держат пальцем. Тост адресуется ПАРОЙ `(chatId, threadRootId)`, а не одним `chatId`: у ветки свой тост поверх тоста её же чата. Любой вызов `onDismiss` обязан передавать оба — иначе тост ветки не находится и не закрывается (ловили на автоскрытии и на смахивании; крестик работал, потому что там оба передавались).

**Ветки (треды)**
- Ответ ветки — обычная строка в `messages` с `thread_root_id`; вложенности нет (`rootForUser` требует `thread_root_id IS NULL`). Из основной ленты ответы вырезаны (`thread_root_id IS NULL` во всех трёх выдачах истории и в `/meta/last`), права/картинки/опросы/идемпотентность — общие с `chat_message`.
- **Счётчик чата и непрочитанное веток — РАЗНЫЕ счётчики, складывать их в один запрос нельзя.** `/unread` считает только то, что гасится открытием самого чата, то есть ленту без ответов веток: ответы в ленту не попадают, клиент шлёт `message_read` по видимым id, и пока ответы веток входили в `/unread`, бейдж чата после прочтения всей переписки висел вечно — снять его было нечем, а участник чата, не отвечавший в ветке, не видит её даже в списке «Ветки». Непрочитанное веток идёт отдельно (плашка под корнем из `attachThreadSummaries` + раздел «Ветки»), и клиент сам прибавляет `threadUnreadTotal` к общему бейджу — поэтому в `/unread` его быть не должно ещё и из-за двойного счёта. Заголовок `X-Miras-Features` для `/unread` больше не при чём; возможности устройств для пушей — отдельный механизм (`device_tokens.capabilities` + `requiredFeature`).
- `threadSummary` считается ПОД КОНКРЕТНОГО ЗРИТЕЛЯ (`unread_count`), поэтому в широковещательном `thread_summary_changed` сводки нет — только `root_id`. Раньше туда клалась сводка отправителя (у него `unread` всегда 0), и по ней у остальных непрочитанное обнулялось бы; клиент её игнорировал и перезапрашивал `/threads/:id/summary` — на это и рассчитываем явно.
- `listThreadsForUser` обязан СНАЧАЛА сузиться до своих веток (CTE `my_roots`: свой корень либо свой ответ) и только потом искать последний ответ каждой. Обратный порядок (коррелированный подзапрос по всем корням архива, участие проверяется после) — 985 мс на 28 тыс. сообщений против 2 мс, при том что список дёргает каждый участник чата на каждый ответ в любой ветке. Ограничение `limit` применяется в JS после `isParticipant`, поэтому само по себе от полного прохода не спасает — мерить надо запрос, а не длину выдачи.
- Персональное «удалить у себя» на корневом сообщении скрывает ВСЮ ветку, включая будущие ответы (`thread_hidden`, отдельная таблица — списком `message_id` это невыразимо). Удаление корня «у всех» мягко удаляет и все ответы (`softDeleteThread`), содержимое в БД остаётся — общее правило хранения переписки действует и здесь.
- Аватар строки в списке «Ветки» — РОДИТЕЛЬСКОГО ЧАТА (`item.chat`, с учётом `kind`: общий/группа/«Избранное» рисуются своими значками, личная переписка — аватаром собеседника), а не автора корневого сообщения. Заголовок строки и так `chat.name`, и рядом с ним стояло чужое лицо: в личной переписке это было собственное лицо зрителя, если корень писал он сам. Данные для всех вариантов приезжают в той же выдаче (`chatMeta` в `services/threads.js`).
- Уведомление о ветке получают только «подписчики» — автор корня и уже отвечавшие. Остальные участники чата ответ видят (доступ общий), но сигнала не получают ни пушем, ни бейджем — только плашка под корнем, если корень на экране.

- **Целей две: `deb` и `tar.gz`, и вторая не для красоты.** У Astra бывает включена замкнутая программная среда, где установка постороннего пакета недоступна; распакованный `tar.gz` запускается без установки и без разрешения зависимостей. НО: SUID на `chrome-sandbox` ставит только `postinst` пакета, в архиве его выставить некому — на защищённом ядре Astra (отключены непривилегированные user namespaces) распакованный архив без `chmod 4755 chrome-sandbox` или `--no-sandbox` не стартует.
- **Минимальная glibc — 2.25** (измерено `readelf -V` по ВСЕМ бинарникам сборки: сам `miraschat-desktop` и `chrome_crashpad_handler` требуют 2.25, остальные ниже; зависимости от `GLIBCXX` нет вовсе — Electron несёт свою). Значит Astra SE 1.7 (Debian 10, glibc 2.28) и новее — работают; Astra SE 1.6 «Смоленск» и CE 2.12 «Орёл» (glibc 2.24) — НЕТ, и это не чинится настройками, только более старым Electron. Проверять версию нужно измерением, а не по номеру Electron: у 33.4.11 требование оказалось заметно ниже ожидаемого.
- `postinst` от electron-builder сам проверяет, работают ли user namespaces, и ставит `chmod 4755` на `chrome-sandbox` только когда они отключены — то есть случай Astra закрыт штатно, свой скрипт не нужен.
- **Секция `linux.desktop` задаётся ПЛОСКО** (`{"Name": …, "Categories": …}`), без обёртки `entry`: вложенная форма появилась в electron-builder 26, а у нас 25 — объект уезжал в `.desktop` строкой `entry=[object Object]`, а имя и категории не применялись вовсе. Ещё `.deb` не соберётся без `homepage` в `package.json` — electron-builder падает с `Please specify project homepage`.
- **Ссылка на скачивание для Astra — свой манифест `linux.json`** в `updates/` (`url` на `.deb`, `archiveUrl` на `tar.gz`, `minGlibc`). Дописывать платформу в `latest.yml` нельзя: он принадлежит `electron-updater`, у него свой формат и своё назначение — автообновление Windows. Кнопки скачивания (`WebDownloadLinks.tsx`) видны ТОЛЬКО в браузерной версии (в Electron и на Android компонент возвращает `null`), поэтому правка кнопок не требует пересборки десктопа и APK — достаточно выложить веб.
- **Ряд кнопок скачивания — только значки, без подписей.** Подписи прятались медиазапросом по ширине ОКНА (`max-width: 1180px`), но список чатов шириной 320px вместе с окном не растягивается: с третьей платформой ряд перестал помещаться на ЛЮБОМ экране, включая 1920 (замерено: нужно 321px, доступно 295px — заголовок списка при этом сжимался в ноль). Текст оставлен в разметке скрытым, чтобы у ссылки было имя для экранных читалок.
- **Автообновления на Linux нет**: `canUpdate` в `main.js` ограничен `win32`, и это верно — `electron-updater` умеет обновлять сам только AppImage, но не `deb`. Linux-клиенты обновляются переустановкой пакета.

- **`electron-builder` на этой машине спотыкается о символьные ссылки.** В его архиве `winCodeSign-2.6.0.7z` лежат macOS-ссылки (`darwin/**/lib/*.dylib`), а их создание на Windows требует прав администратора или Developer Mode — ни того, ни другого нет, и сборка падала на распаковке (`Cannot create symbolic link`, 4 попытки подряд). Лечится один раз и навсегда: распаковать архив ВРУЧНУЮ мимо macOS-папки в тот каталог, куда его кладёт сам билдер, — `7za x -y <любой .7z из кэша> -oC:\Users\Gri\AppData\Local\electron-builder\Cache\winCodeSign\winCodeSign-2.6.0 -x!darwin`, затем убрать из кэша мусорные числовые каталоги неудачных попыток. Имя `winCodeSign-2.6.0` не произвольное: билдер ищет `<name>-<version>` и, найдя готовый каталог, распаковку пропускает. Для Windows-сборки содержимое `darwin/` не нужно вовсе — там подписывание для macOS. Подписи у нас всё равно нет (`no signing info identified, signing is skipped`), но каталог требуется и ради `rcedit`.
- `npx cap sync` переписывает `capacitor.build.gradle`/`capacitor.settings.gradle` с CRLF — в `git status` они всплывают как изменённые, хотя содержимое то же. Перед коммитом их надо откатывать (`git checkout --`), иначе в диффе будет мусор.

**Подпись Android-сборки — единственный ключ, и он не в репозитории**
- APK раздаются как **debug**-сборки (`MirasChat-<версия>-debug.apk`), то есть подписаны обычным `~/.android/debug.keystore`. Android ставит обновление поверх установленного, ТОЛЬКО если подпись совпадает; иначе `INSTALL_FAILED_UPDATE_INCOMPATIBLE` — человеку придётся удалить приложение и войти заново. Версия и `versionCode` тут ни при чём.
- `debug.keystore` генерируется на каждой машине СВОЙ при первой сборке. Прод 1.7.0 подписан ключом с SHA-256 `72f2b66fa7e8f405d00adb804ff7a8dec3d41383235de0b7d0517a9379440476`. На новой машине (12.08.2026) сборка завела свой ключ `c73d5c0656ad9f20d7e49417d57d6c296d2718eb9ece40d91c2b74c6079b05f1` — собранный ей APK НЕ встал бы поверх установленного ни у кого.
- **Перед первой боевой сборкой на новой машине обязательно перенести `%USERPROFILE%\.android\debug.keystore` со старой** и после сборки сверить отпечаток: `apksigner verify --print-certs <apk>` должен дать `72f2b6…0476`. Копии ключа на прод-сервере НЕТ (проверено) — единственный экземпляр лежит на старом компьютере. Потеря этого файла = ни одного обновления больше никогда, всем переустанавливать вручную; резервная копия обязательна.
- Перевод на нормальный release-keystore эту проблему задним числом не решает: любой другой ключ так же требует переустановки у всех.

**Правила деплоя**
- Команда «Отправить/Отправляй» = полный цикл: коммит+пуш, деплой сервер+веб, перезапуск сервера, бамп версий win+apk, сборка обеих, заливка с проверкой sha512, чистка старых файлов только после проверки хешей.
- Прод-сервер: `ssh miraschat` (алиас на машине пользователя, ключ без пароля) → `gri@cagrizzz.ru`, процесс `MirasChatServer` в pm2 (порт 3010; `fp`/`rpf` в том же pm2 — чужие проекты, не трогать). Перезапуск — `pm2 restart MirasChatServer`. Код на проде: `/home/gri/projects/miraschat` (тот же git-репозиторий, деплой через `git pull`), веб-сборка раздаётся из `/var/www/miraschat/dist`, файлы обновлений — `/var/www/miraschat/updates`.
- **Выкладка веба `sudo` больше НЕ требует** (12.08.2026): `/var/www/miraschat/dist` передан пользователю `gri` (`chown -R gri:www-data`, права `u=rwX,go=rX` — nginx читает как раньше). Команда: `rsync -a --delete /home/gri/projects/miraschat/client/build/ /var/www/miraschat/dist/`. Значит весь цикл «Отправляй» проходит без участия человека — раньше упирался ровно в этот шаг, потому что `sudo` на проде спрашивает пароль (и через `ssh host "команда"` не работает вовсе: нужен `-t`, иначе «A terminal is required»). Остальное (git pull, сборка клиента на проде, `pm2 restart`, заливка `.exe`/`.apk` в `updates/`) и раньше шло без `sudo`. На заметку: неудачный `rsync` без прав безопасен — падает ДО записи и удаления, прежняя выкладка остаётся целой.
- Собранные билды (win .exe + android .apk) складывать в `NBRT_Chat/release/`. Имена файлов: `(имя приложения)_Setup_(версия).exe` и `(имя приложения)_(версия)-debug.apk` — версия вида `1.7.0`.
- «Собери, но не отправляй» = коммит+пуш кода (включая правки конфигурации сборки) + деплой сервер+веб делаются как обычно, но собранные win/apk-артефакты НЕ заливаются на прод — только собираются локально и проверяются (`aapt2 dump badging`, сверка sha512 инсталлятора с `latest.yml`). Значит выкладку `scp`/обновление `android.json`.
- **`desktop/package.json`: `nsis.artifactName` — ловушка.** Раньше был захардкожен буквальной строкой версии (`"MirasChat Setup 1.6.10.${ext}"` — с горячего фикса `1b5968e`, откуда и завелась пара `releaseVersion`/`buildVersion`, отдельная от `version` — нужна была, чтобы `electron-updater` сравнивал semver по одному полю, а в интерфейсе показывалась другая метка). После хотфикса вернуть на `${version}` забыли, и каждый следующий релиз строку просто перепечатывали руками — 11.08.2026 на этом словили реальный баг: `version` подняли до 1.7.0, а `artifactName` остался `1.6.10`, из-за чего `electron-builder` собрал `latest.yml` с `version: 1.7.0`, но `url`/`path` внутри указывали на `MirasChat Setup 1.6.10.exe` — разъехавшиеся имя и версия внутри одного манифеста. Исправлено на шаблон `${version}` — эта категория ошибок больше не может повториться. `releaseVersion`/`buildVersion` остались отдельными полями (механизм хотфика может понадобиться снова), но теперь синхронизированы с `version` при каждом бампе.
