# Реестр рисков безопасности

Дата аудита: 2026-08-10.

Этот файл фиксирует обнаруженные риски для отдельного обсуждения. Они намеренно не смешиваются с функциональными исправлениями без согласования архитектуры, совместимости клиентов и порядка ротации ключей.

## Критический приоритет

### SEC-001 — смешение типов JWT

- Обычные пользовательские, супер-админские и токены сброса пароля подписываются одним `JWT_SECRET`.
- `middleware/verifyToken.js` проверяет только подпись и принимает токен без проверки его назначения, `issuer`, `audience` или отдельного `token_type`.
- `index.js` в событии `user_online` также принимает любой JWT с полем `id`.
- Следствие: reset-токен или токен супер-админа может быть принят как пользовательская сессия. При совпадении числового ID возможен доступ к REST API и персональной WebSocket-комнате пользователя.

Предлагаемое решение:

1. Ввести обязательный `token_type`: `user_access`, `password_reset`, `superadmin_access`.
2. Проверять `issuer`, `audience`, алгоритм подписи и `token_type` в каждом middleware.
3. Использовать отдельные секреты или, предпочтительно, отдельные асимметричные ключи для пользовательских и административных токенов.
4. В WebSocket использовать middleware аутентификации на этапе handshake, а не отдельное событие после подключения.

### SEC-002 — публичный fallback для JWT-секрета

- При отсутствии переменной окружения используется строка `your_super_secret_key`.
- С таким сервером любой может самостоятельно подписать пользовательский или супер-админский токен.

Предлагаемое решение: валидировать секрет до запуска HTTP-сервера и завершать процесс с ошибкой, если секрет отсутствует, совпадает с примером или недостаточно длинный. Перед внедрением нужна ротация секрета на сервере и принудительный выход всех клиентов.

## Высокий приоритет

### SEC-003 — слабая защита обычного входа и регистрации

- Для `/api/auth/login`, `/register` и выдачи reset-токена нет общего rate limit.
- Минимальная длина пароля — пять символов.
- Не задан верхний предел с учётом 72-байтового эффективного ограничения bcrypt.

Предлагаемое решение: лимиты по IP и логину, прогрессивная задержка, журналирование атак, пароль минимум 10–12 символов и проверка длины в UTF-8 байтах до bcrypt.

### SEC-004 — бессрочные и неотзываемые пользовательские токены

- Пользовательский JWT не имеет `expiresIn`.
- Смена пароля, блокировка или удаление сессии не отзывают уже выданный токен.

Предлагаемое решение: access-токен на 10–30 минут, ротируемая refresh-сессия в БД, `session_version` у пользователя и интерфейс завершения активных сессий.

### SEC-005 — недостаточная изоляция WebSocket-сессий

- Один сокет может повторно вызвать `user_online` с другим токеном и остаться в ранее присоединённых комнатах.
- `typing` и `stop_typing` доверяют присланным `userId` и `username`, не проверяют аутентификацию и участие в чате.
- Для большинства событий, кроме отправки сообщений, нет частотных лимитов.

Предлагаемое решение: аутентификация handshake, неизменяемый `socket.data.userId`, выход из старых комнат при повторной авторизации, серверное формирование identity и общий per-user/per-event rate limit.

### SEC-006 — истощение памяти и диска через загрузки

- Изображения до 20 МБ целиком принимаются в память.
- Нет пользовательской квоты, общего лимита хранилища и частотного ограничения.
- Файл загружается до создания сообщения; брошенные загрузки не очищаются.

Предлагаемое решение: потоковая обработка, лимиты одновременных загрузок и байтов на пользователя, таблица временных загрузок с владельцем и TTL, периодическая уборка orphan-файлов.

### SEC-007 — изображения чатов доступны без авторизации

- Вся папка `/api/uploads` раздаётся как открытая статика.
- Получив URL изображения из приватного чата, его можно скачать без токена.

Предлагаемое решение: авторизованный download endpoint с привязкой файла к сообщению и проверкой участия в чате; для аватаров можно оставить отдельную публичную политику.

### SEC-008 — незашифрованные архивы удалённых пользователей

- Архивы содержат профиль, переписку, контакты, события и другую персональную информацию в JSON.
- Шифрование, срок хранения и автоматическое удаление не определены.

Предлагаемое решение: шифрование отдельным ключом, права доступа каталога, журнал выгрузок, регламент TTL и защищённый механизм восстановления.

### SEC-009 — доверие к `X-Forwarded-For`

- IP сокетов и rate limit супер-админа читают `X-Forwarded-For` напрямую.
- Без гарантированной фильтрации заголовка доверенным reverse proxy адрес можно подделать и обойти лимиты.

Предлагаемое решение: настроить `trust proxy` только на известные прокси, использовать `req.ip` после этой настройки и удалять внешний `X-Forwarded-For` на границе.

## Средний приоритет

### SEC-010 — произвольные внешние URL в Electron

- Любой URL из `window.open` передаётся в `shell.openExternal`.
- Не ограничены протоколы и доверенные домены.

Предлагаемое решение: разрешать только `https:` и явный allowlist доменов; отклонять `file:`, `javascript:`, `data:` и неизвестные custom schemes.

### SEC-011 — токены в `localStorage` и отсутствие CSP

- Пользовательский и супер-админский токены доступны любому JavaScript в origin приложения.
- В HTML нет Content Security Policy.

Предлагаемое решение: строгая CSP, запрет inline/eval, аудит всех внешних ресурсов. Для веба рассмотреть защищённые `HttpOnly; Secure; SameSite` cookies; для Electron — хранилище main-процесса с узким IPC.

### SEC-012 — CORS разрешён всем источникам

- REST и Socket.IO используют неограниченный origin.

Предлагаемое решение: allowlist production-origin, отдельные настройки для web/Electron/mobile и явная политика credentials/headers.

### SEC-013 — Android backup включён

- `android:allowBackup="true"` позволяет резервировать данные WebView, в которых находится пользовательский токен.

Предлагаемое решение: отключить backup или задать `dataExtractionRules`, исключающие токены и WebView storage.

### SEC-014 — Firebase API key в репозитории

- `google-services.json` содержит клиентский Firebase API key. Это штатный публичный идентификатор, но он требует внешних ограничений.

Предлагаемое решение: проверить ограничения ключа по Android package/SHA и список разрешённых API в Google Cloud Console.

### SEC-015 — подпись Electron-релизов не подтверждена конфигурацией репозитория

- Используется автоматическая установка обновлений с generic HTTPS provider.
- В репозитории не видна обязательная настройка сертификата Authenticode; возможно, она хранится только в CI.

Предлагаемое решение: документировать обязательную подпись, отклонять неподписанные артефакты в CI и проверить реальный установщик/обновление через `Get-AuthenticodeSignature`.

### SEC-016 — постоянная очередь хранит текст сообщений в профиле WebView

- Для восстановления после аварии исходящие сообщения сохраняются в
  `localStorage` до серверного подтверждения.
- Это обеспечивает доставку, но данные лежат на устройстве в открытом виде и
  доступны JavaScript-коду того же origin; риск усиливает SEC-011.

Предлагаемое решение: вместе с решением SEC-011 перенести очередь в шифрованное
хранилище платформы (Electron safeStorage / Android Keystore с локальной БД),
предусмотреть очистку очереди при безопасном выходе и политику хранения для
управляемых устройств. До этого не выводить содержимое очереди в логи и
разделять записи по `userId` — разделение уже реализовано.
